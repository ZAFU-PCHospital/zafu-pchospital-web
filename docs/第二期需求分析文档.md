# 电脑医院官网第二期需求设计文档

> 阶段定位：内部成员系统与维修数据平台
> 版本：Phase 2
> 状态：需求设计稿
> 数据库：GreatSQL 8.x
> 本文档建立在第一期官网基础之上，第二期重点建设成员登录、成员工作台、维修记录、统计排行与内部交流能力。

---

# 1. 第二期目标

第二期的核心目标是将第一期的公开展示型官网扩展为：

> **电脑医院内部成员工作平台 + 维修数据沉淀平台**

主要解决以下问题：

1. 成员拥有独立账号并可登录内部工作台。
2. 维修完成后能够规范提交维修记录。
3. 每名成员拥有独立维修数据统计。
4. 管理员能够审核和管理维修记录。
5. 成员之间可以围绕维修案例进行交流讨论。
6. 网站可以基于真实维修数据展示社团服务成果。
7. 将官网“加入我们”页面的报名信息正式入库，形成可追踪的招募流程。
8. 管理员能够查看报名、记录面试结论，并在通过后自动创建或升级成员账号。
9. 支持初始成员凭有效邀请码自助注册并自动获得成员身份。
10. 为后续外部用户系统、QQ/微信登录、活动系统等功能预留扩展能力。

# 5. 登录系统与统一账号边界

## 5.1 第二期初始登录方式

第二期内部成员可以暂时使用：

```text
QQ号 + 密码
```

登录。

QQ 号可以作为当前阶段的登录凭据之一，但只能通过独立身份/凭据记录映射到 `User.id`。业务表、权限判断和外键一律引用 `User.id` 或 `MemberProfile.id`，不得引用 QQ 号充当用户主键。

后续接入手机号验证码、QQ OAuth、微信 OAuth 时，应在同一个 `User` 上增加或绑定登录身份，不得重新创建割裂账户。

# 6. 成员账号创建与发放

普通公开注册不得直接获得成员身份。第二期允许以下三种受控来源创建或升级成员：

1. 管理员直接创建成员。
2. 新成员报名面试通过后，由系统自动创建或升级成员。
3. 初始成员使用有效邀请码注册，校验成功后自动成为成员。

管理员直接创建成员时可录入：

- 姓名 / 昵称
- QQ号
- 初始密码
- 成员身份
- 可选技能标签

成员首次登录后必须修改初始密码。

报名通过后的账号发放必须在单个事务或可安全重试的幂等流程中完成：

```text
锁定报名记录
    ↓
按手机号 / QQ / 已绑定身份查找现有 User
    ↓
复用现有 User 或创建新 User
    ↓
创建或激活 MemberProfile
    ↓
授予 MEMBER 角色
    ↓
生成一次性初始化凭据或账号领取令牌
    ↓
记录 AccountProvision 与 AuditLog
```

同一报名重复点击“通过”不得创建重复 `User`、`MemberProfile` 或角色关系。若账号发放失败，报名保留为“已通过但发放失败”，管理员可基于同一幂等键重试。

# 7. 密码要求

数据库中禁止保存明文密码。

密码必须通过安全密码哈希算法保存。

首次登录流程：

```text
管理员创建账号 / 报名通过 / 邀请码注册
    ↓
成员获得登录标识 + 初始密码或一次性初始化凭据
    ↓
首次登录
    ↓
系统要求修改密码
    ↓
修改成功
    ↓
进入成员工作台
```

# 11. 新成员报名、面试与邀请码

## 11.1 官网报名入库

`/join` 页面现有登记表必须从“本地回执”升级为真实服务端提交。至少采集：

- 姓名
- QQ 号
- 手机号
- 可选自我介绍、意向方向或备注
- 隐私告知确认时间
- 来源页面与提交时间

服务端必须重新校验字段，不得只依赖浏览器原生校验。提交成功后返回不可猜测的报名 ID 与回执号；不得在响应或 URL 中回显完整手机号等敏感信息。

重复报名按“同一招募批次 + 规范化手机号或 QQ”识别。默认返回现有有效报名的回执，不创建重复记录；已撤回或已结束报名的再次提交规则由管理员配置或产品确认。

## 11.2 报名状态

`JoinApplicationStatus` 建议固定为：

```text
SUBMITTED           已提交
INTERVIEW_PENDING   待面试
INTERVIEW_PASSED    面试通过
INTERVIEW_REJECTED  面试未通过
WITHDRAWN           已撤回
```

账号发放使用独立状态 `ProvisionStatus`：

```text
NOT_REQUIRED  尚未触发
PENDING       待发放
SUCCEEDED     发放成功
FAILED        发放失败，可重试
```

报名状态与账号发放状态不得混成一个枚举。面试未通过不会删除报名数据；面试通过但账号发放失败时，也不能把面试结果回滚为未通过。

## 11.3 管理员处理流程

管理员后台可以：

- 分页查看、搜索和筛选报名记录
- 查看报名详情与历史状态
- 填写面试时间、面试结果和内部备注
- 将结果标记为通过、未通过或撤回
- 查看自动发放结果并对失败任务执行幂等重试

状态流转：

```text
SUBMITTED → INTERVIEW_PENDING → INTERVIEW_PASSED
                              ↘ INTERVIEW_REJECTED
SUBMITTED / INTERVIEW_PENDING → WITHDRAWN
```

只有 `SUBMITTED` 或 `INTERVIEW_PENDING` 可登记面试结果。终态变更必须要求管理员填写原因，并写入审计日志。

## 11.4 面试通过后自动发放成员账号

管理员提交“面试通过”后，服务端在事务内或事务 + 可靠任务机制中执行：

1. 保存面试结论、操作者与时间。
2. 创建 `AccountProvision`，使用 `JOIN_APPLICATION:<applicationId>` 作为幂等来源。
3. 查找并复用已存在的统一 `User`，不存在时创建。
4. 创建或激活唯一 `MemberProfile`，授予 `MEMBER` 角色。
5. 生成一次性初始化凭据；凭据明文最多展示或发送一次，数据库只保存哈希。
6. 将发放结果、失败原因摘要和关联用户写入日志。

若报名信息与现有多个账号发生冲突，必须停止自动合并并进入人工处理，禁止根据 QQ 号直接覆盖用户关系。

## 11.5 初始成员邀请码注册

初始成员可通过 `/register/member` 填写有效邀请码并完成注册。邀请码仅是获得成员资格的授权凭证，不是永久登录凭据。

邀请码至少支持：

- 唯一代码的哈希保存
- 创建者、生效时间、失效时间、最大使用次数和已使用次数
- 可选绑定 QQ、手机号或招募批次
- 未生效、启用、耗尽、过期、撤销状态
- 每次成功或失败使用的安全审计记录

同一个邀请码可以被多名初始成员重复使用，直到达到管理员设置的最大使用次数、超过失效时间或被撤销。管理员可在后台调整生效时间、失效时间和最大使用次数；`usedCount` 由成功消费事务自动累计，只读不可手工改写。调整后的 `maxUses` 不得小于 `usedCount`。

注册时必须在事务中锁定邀请码，校验状态、有效期、使用次数和可选绑定条件；随后创建或复用 `User`、创建 `MemberProfile`、授予 `MEMBER` 角色并增加使用次数。并发提交只能有一笔成功消费最后一个名额。

邀请码不得通过明文日志、分析平台、URL 查询参数或客户端持久化暴露。管理员创建邀请码后，明文只显示一次。

## 11.6 招募数据隐私

- 报名详情、面试备注和邀请码管理仅管理员及社长可访问。
- 普通成员不得查看报名列表或管理员备注。
- 手机号、QQ 等敏感字段在列表页默认脱敏，只有具备对应权限时可查看完整值。
- 公开页面不得通过“手机号/QQ 是否存在”暴露用户或报名状态。
- 报名数据的保留期限与删除申请流程需由社团确认；在确认前不得自动物理删除。

# 39. 推荐核心数据实体

初步建议：

```text
User
Role
MemberProfile
UserRole
AuthIdentity / PasswordCredential

JoinApplication
JoinApplicationReview
InviteCode
InviteCodeRedemption
AccountProvision

Skill
UserSkill

RepairRecord
RepairPhoto
RepairCategory

RepairComment
RepairFavorite

RepairAuditLog
RepairTimeline

Notification
AuditLog
```

未来可加入：

```text
ExternalIdentity
QQIdentity
WeChatIdentity
```

实体边界：

- `User` 是统一账户本体，不保存招募流程状态。
- `Role` / `UserRole` 表达授权，不用 `MemberProfile` 字段替代完整 RBAC。
- `MemberProfile` 是成员资料，一名有效用户最多一个有效成员档案。
- `JoinApplication` 是公开报名记录，可在没有 `User` 的情况下存在。
- `JoinApplicationReview` 保存每次面试处理，不覆盖历史。
- `InviteCode` 保存邀请码策略与哈希，不保存可再次读取的明文。
- `InviteCodeRedemption` 保存邀请码消费事实，一次成功消费对应一个用户。
- `AccountProvision` 保存从报名或邀请码到账号创建/升级的幂等执行结果。
- `AuditLog` 是跨领域管理操作日志；`RepairAuditLog` 可保留为维修领域明细，但不得与全局审计职责混淆。

## 39.1 JoinApplication 建议字段

```text
id
ticketNo
recruitmentCycle
realName
qq
phone
selfIntroduction / preferredDirection / applicantRemark（可选）
status
provisionStatus
privacyConsentAt
submittedAt
lastReviewedAt（可选）
createdAt / updatedAt / deletedAt
```

QQ 与手机号是报名联系方式和账户匹配线索，不是外键。与账号建立关系时通过 `AccountProvision.userId` 记录最终结果。

## 39.2 JoinApplicationReview 建议字段

```text
id
applicationId
result
interviewedAt
reviewerUserId
internalNote（可选）
createdAt
```

每次处理新增一条记录，禁止覆盖旧记录。`internalNote` 仅管理员可见，并应限制长度。

## 39.3 InviteCode 建议字段

```text
id
codeDigest
displayPrefix
status
activeFrom
expiresAt
maxUses
usedCount
boundQq / boundPhone（可选）
createdByUserId
createdAt / updatedAt / revokedAt / deletedAt
```

`codeDigest` 使用带服务端 pepper 的安全摘要进行比对；数据库不保存可还原的邀请码明文。`NOT_STARTED`、`EXPIRED`、`EXHAUSTED` 可根据时间与计数计算，避免存储状态与事实不一致。

## 39.4 InviteCodeRedemption 建议字段

```text
id
inviteCodeId
userId
memberProfileId
idempotencyKey
redeemedAt
```

只有成功消费才创建使用记录；失败尝试写安全审计或限流日志，不记录邀请码明文。

## 39.5 AccountProvision 建议字段

```text
id
sourceType
sourceId
idempotencyKey
status
userId（可选）
memberProfileId（可选）
attemptCount
lastErrorCode（可选）
createdAt / updatedAt / completedAt（可选）
```

`sourceType + sourceId` 与 `idempotencyKey` 均应具有唯一约束，保证同一报名或邀请码消费不会重复发放账号。

# 41. 权限原则

必须做到：

> 后端权限校验不能依赖前端按钮是否显示。

例如普通成员即使手工调用管理员接口，也必须被后端拒绝。

所有：

- 修改
- 删除
- 审核
- 管理成员
- 查看或处理报名
- 发放成员账号
- 创建、撤销或查看邀请码

操作必须进行服务端权限验证。

最低权限建议：

```text
join:submit                 公开提交，带限流与风控
join:read                   管理员 / 社长
join:review                 管理员 / 社长
member:provision            管理员 / 社长或受控系统任务
invite:create               管理员 / 社长
invite:revoke               管理员 / 社长
invite:read                 管理员 / 社长
invite:redeem               持有效邀请码的注册流程
audit:read                  管理员 / 社长，按策略限制
```

“系统自动发放”使用受控服务身份执行，但审计日志必须同时记录触发该流程的管理员或邀请码来源。

# 44. 删除策略

重要数据尽量采用软删除。

例如：

```text
deleted_at
```

而不是直接物理删除。

适用于：

- 报名记录
- 维修记录
- 评论
- 成员
- 邀请码（业务上撤销；不得删除已存在的使用记录）

避免误操作导致数据永久丢失。

软删除后：

- 默认业务查询必须排除 `deletedAt IS NOT NULL` 的记录；
- 唯一性约束不能只依赖应用层，需为 GreatSQL 设计可执行的唯一键或等价约束策略；
- 被撤销成员保留原 `User` 与历史业务归属，仅移除或失效成员资格；
- `InviteCodeRedemption`、`AccountProvision` 与 `AuditLog` 原则上不可软删除，只允许按合规策略归档。

# 45. 审计原则

管理员的重要操作建议留痕：

- 审核
- 退回
- 修改记录
- 删除记录
- 重置成员密码
- 禁用成员
- 查看完整报名敏感信息
- 修改报名状态或面试结论
- 自动或手动重试账号发放
- 创建、撤销、消费邀请码
- 绑定、合并或冲突处理统一账户

后续出现数据争议时可以追踪。

审计记录至少包含：

- 操作者用户 ID / 系统身份
- 动作类型
- 目标实体类型与 ID
- 请求关联 ID
- 变更前后摘要（敏感字段脱敏）
- 结果与失败码
- 创建时间

密码、邀请码明文、会话令牌、验证码和完整密钥禁止写入审计日志。

## 45.1 GreatSQL 数据库约束

第二期数据库确定使用 **GreatSQL 8.x**，按 MySQL 8.0 兼容协议接入。所有业务表使用 InnoDB、`utf8mb4` 字符集和统一排序规则；具体 GreatSQL 小版本、排序规则与时区在 M0 锁定并写入环境说明。

基础约定：

- 核心 ID 统一使用 UUID 字符串，并在应用层统一生成。
- 时间统一以 UTC 写入 `DATETIME(3)`，API 使用 ISO 8601 字符串返回。
- 枚举在应用契约中集中定义；数据库可使用受控字符串列或 ORM 映射，不得由各模块自行拼写。
- 账号发放、邀请码消费、角色授予必须使用事务与唯一约束保证一致性。
- 生产迁移只能前向执行，禁止以 `db push` 或手工改表替代版本化 migration。

## 45.2 页面与 API 能力

第二期至少提供以下招募相关接口能力，实际前缀统一使用 `/api/v1`：

```text
POST   /api/v1/join-applications
GET    /api/v1/admin/join-applications
GET    /api/v1/admin/join-applications/:id
POST   /api/v1/admin/join-applications/:id/reviews
POST   /api/v1/admin/join-applications/:id/provision/retry
POST   /api/v1/admin/invite-codes
GET    /api/v1/admin/invite-codes
PATCH  /api/v1/admin/invite-codes/:id
POST   /api/v1/admin/invite-codes/:id/revoke
POST   /api/v1/member-registrations/invite
GET    /api/v1/me
```

要求：

- 公开提交接口必须限流，并统一处理重复提交。
- 管理接口必须服务端鉴权与权限校验。
- 状态变更接口校验合法前置状态，拒绝跳跃或重复副作用。
- 创建类接口支持 `Idempotency-Key` 或等价幂等机制。
- API 返回统一成功/错误信封、稳定错误码与 `requestId`。
- 列表接口支持分页、状态筛选、时间范围与脱敏搜索。

- lint、build、migration、契约测试与关键并发测试通过。

# 49. 第二期核心产品逻辑

第二期不应该只是：

> “做一个成员后台。”

真正应该形成的是：

```text
一次报名 / 一次邀请
     ↓
可审计的成员身份建立
     ↓
统一 User + Role + MemberProfile
     ↓
一次维修
     ↓
一条结构化维修记录
     ↓
成员个人数据
     ↓
社团整体数据
     ↓
内部经验交流
     ↓
典型案例沉淀
     ↓
官网成果展示 / 技术文档
```

最终让每一次真实维修行为，都能够沉淀为电脑医院自己的数据与知识资产。
