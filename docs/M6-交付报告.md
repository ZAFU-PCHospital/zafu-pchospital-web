  **不改变审核状态**（`APPROVED` 改完仍是 `APPROVED`，不引入快照表，改动前后差异留在
  审计与时间线里）

- 软删除：直接复用 M2 的 `repairService.softDelete`（它本来就不校验归属），不另写删除逻辑

### 分类管理（§65）

- 管理端列表含**已停用**分类并带 `usedByRepairCount` 引用计数（回答「能不能删 / 有没有人用」）
- 新增 / 修改 / 停用 / **重新启用**（误停用后只能新建同名分类会把历史记录劈成两份）
- 重复 code 返回 409 `REPAIR_CATEGORY_CODE_CONFLICT`，不再让 Prisma 唯一键冲突冒泡成 500
- 停用 / 启用前锁行校验存在性，不存在的 id 统一 `RESOURCE_NOT_FOUND`

### 数据导出（§67 / 需求 §34）

- `GET /api/v1/admin/repairs/export?format=csv|xlsx` + 与列表**完全同源**的筛选参数
- 一条数据路径（`RepairExportRow[]`）+ 两个出口（`export-csv.ts` / `export-xlsx.ts`）
- CSV：UTF-8 BOM（Excel 打开中文不乱码）+ CRLF（RFC 4180）+ 字段转义 +
  **公式注入防护**（`=`/`+`/`-`/`@` 开头前置单引号）
- XLSX：`exceljs` 生成真 `.xlsx`，表头加粗、首行冻结、记录 ID 与照片 URL 按**文本**写入
- 图片不嵌入表格，只输出记录 ID 与照片 URL；行数上限 20000，超出**拒绝而不是截断**
- 每次导出写审计 `repair.exported`（导出等于把成员姓名等带出系统）

## 数据库与性能

### Migration

- **本次无 Migration**。批 1 的全部能力都建立在既有表上：
  - 成员列表/详情/编辑 → `member_profiles`、`users`、`user_identities`、`user_roles`、`user_skills`
  - 角色设置 → `user_roles` 既有 `activeKey` 唯一键与 `revokedAt`
  - 分类引用计数 → `repair_records.category_id` 上的既有索引
  - 导出 → `repair_records` 既有索引（`repairDate` + `createdAt` 排序）
  - 审计 → `audit_logs` 既有三个索引
- 因此未触碰 `tests/unit/migration-contract.test.ts`，也没有前向 Migration 需要复核。

### 查询与性能说明

- 成员列表：一次 `count` + 一次分页 `findMany` + 一次 `groupBy`（只统计当前页成员的
  已通过维修数），没有 N+1。
- 导出：字段裁剪到导出真正需要的列（不带 `reviews` / `timeline`），
  `take = EXPORT_MAX_ROWS + 1` 判断超限，避免额外的一次 `count`。
- 批量操作是 N 次单条事务（上限 50），不是一条大事务：牺牲一点吞吐换取「逐条走完整状态
  规则 + 逐条审计 + 可部分成功」，这是本模块明确选择的取舍。

## 权限与隐私

- 所有管理端方法在 **Service 层** `requirePermission`；前端守卫只是「页面能不能渲染」的第一道
  闸门（需求 §41：后端权限校验不能依赖前端按钮是否显示）
- 已用真实 HTTP 验证：普通成员会话访问 `/api/v1/admin/members`、`/admin/repairs`、导出、
  审核一律 403；未登录 401（见下「路由层端到端」）
- 成员列表不返回明文联系方式；详情读取（明文）与导出（把数据带出系统）都写审计
- 审计摘要经 `redactAuditSummary` 自动脱敏 QQ / 手机号 / 凭据类字段，明文不进日志

## 交互与排版修复（首轮人工验收之后）

首轮验收在真实浏览器里走查后提出四个问题，逐个定位并修复。

### 1. 成员详情要自己往下翻 → 改成窗口

- **现象**：点「详情」后页面看起来没反应，得自己往下滚才在表格底下找到详情内容。
- **原因**：`MemberDetailPanel` 是内联渲染在 `.admin-workspace__content` 末尾的普通 `<Card>`；
  成员表 20 行、页高约 2475px，而「详情」按钮在表格行里，内容却在页面最底部。
- **修复**：新增 `components/admin/AdminModal.tsx`，成员详情与记录详情都改为窗口呈现。
  遮罩按 `docs/design-system.md` §4.5「底色加深 + 全屏遮罩」取 `--bg-deep`（92%），不引入投影；
  `role="dialog"` + `aria-modal` + `aria-labelledby`、`Esc` 关闭、打开时锁定 `body` 滚动、
  焦点落在窗口容器、关闭后归还给触发按钮 —— 与 `layout/Header.tsx` 的移动端索引浮层同构。
- **必须走 `createPortal(document.body)`**：页面内容在 `<main>` 的层叠上下文里，直接写
  `z-index: 96` 只能压住 `<main>` 内部的东西；桌面索引栏（`.rail`，z-index 80）与移动端顶栏
  （`.topbar`，85）挂在根层，会穿过遮罩浮在窗口上面。这一条是实测发现的（窗口左侧那一竖条
  仍是亮的），已写入 `docs/design-system.md` §4.7。
- 实测（CDP，1440×1000，页面先滚到 1474px 再点详情）：窗口 `top=60 / bottom=940` 恒在视口内，
  `aria-modal="true"`、`aria-labelledby` 存在、`focusInDialog: true`、`bodyOverflow: "hidden"`；
  按 `Esc` 后 `dialog: false` 且滚动锁定解除。

### 2. 卡片内容顶着左上角 → 补内边距与内部节奏

- **现象**：「新增成员 / 新增分类 / 成员详情 / 记录详情」这类卡片像「样式没加载出来的纯文本」，
  标题与控件贴着左上边，段与段之间也没有间距。
- **原因**：`.card` 只给描边、底色与圆角，**自身没有内边距**（`/docs` 的预览卡由
  `.docpreview__bar` / `__body` 各自带 padding）。后台把表单直接放进 `<Card>` 就露馅了。
- **修复**：新增 `.admin-panel`（内边距 `clamp(1.25rem, 2.6vw, 1.75rem)` + `gap: --s-5`），
  后台所有卡片式表单都改用它；窗口内各段用 `--line-soft` 细线分隔，不再套第二层卡片。

  最大 2.75rem），导致「新增分类」和页面标题「故障分类」一样大。新增 `.admin-panel__title`

### 3. 数据导出「能导出但没数据」→ 是筛选条件没命中，界面没说清

先取证再改：导出每次都写审计（`repair.exported`），`after_summary` 里带 `filter` 与 `rowCount`。

```
12:30:39 {"filter":{"query":"test_1"},"format":"XLSX","rowCount":0}
12:30:51 {"filter":{"query":"test_1"},"format":"CSV","rowCount":0}
12:31:19 {"filter":{"query":"test_1","repairDateFrom":"1975-12-30","repairDateTo":"2026-09-22"},"format":"CSV","rowCount":0}
```

**结论：导出链路本身是好的**（同一账号不带筛选时 `rowCount: 10`，CSV 1809 字节 / XLSX 8078 字节，
`dimension ref="A1:I11"` 即表头 1 行 + 数据 10 行），当时「没数据」是因为筛选条件
（关键词 `test_1`，另一次还带上了 `1975-12-30` 的起始日期）确实一条都没命中，
而界面只回了一句「已开始下载」，用户打开文件才发现是空表 —— **这是我们没把空结果讲清楚**。

- **修复**：面板改为「先统计、后导出」——
  1. 进页面与每次改筛选后（400ms 防抖）用列表接口 `GET /api/v1/admin/repairs?pageSize=1`
     读 `meta.pagination.total`，在导出按钮旁实时显示「当前筛选条件匹配 N 条记录」；
  2. `N = 0` 时文案直接变成「导出的文件会是空的」并转为告警样式；
  3. 提交时若响应头 `X-Export-Row-Count: 0`，**不生成文件**，并把当时生效的筛选条件原样列出
     （如「内容 / 备注 / 成员『test_1』」），让管理员一眼看出该改哪个条件。
- 实测：`test_1` → 预览 0 条 → 点导出 → 落盘文件数 0、提示列出筛选条件；清空关键词 → 预览 10 条
  → 导出得到 10 行 CSV。
- 顺带修掉一个潜在缺陷：原先 `URL.revokeObjectURL` 紧跟 `anchor.click()`，部分浏览器会把刚开始的
  下载掐断（表现为 0 字节文件），现在推迟一拍释放。

### 4. 停用/启用会跳回页面顶部 → 重载期间不再卸载表格

- **原因**：`CategoryAdminPanel.load()` 一开始就 `setState("loading")`，而表格是
  `{state === "ready" ? … : null}` 条件渲染 —— 表格被卸载后页面高度瞬间从 1765px 塌到几百像素，
  浏览器把滚动位置夹回顶部；等数据回来表格重新挂载，用户已经停在页首。
- **修复**：三个面板（成员、维修、分类）的 `load()` 改成「只有首次加载才切到 loading」，
  重载时保持 `ready`、原地替换行数据。成员与维修管理里的禁用/启用、批量操作同样受益。
- 实测（视口 1440×700，先让表格滚到中段）：点「停用」后**最后一行在视口中的位置 612px → 611px**，
  只有状态行插入导致 `scrollY` 由 772 → 819（浏览器滚动锚定），内容零位移、表格始终挂载。

## 第十一轮验收修复（拖动排序与整块移动 / 手柄同步 / 查看只有一个 / 密码长度 6 位 / 测试库闸门）

第十轮之后提了三条，外加一个「给我一个能快速验证的号」。

### 1. 六点手柄：与复选框同步出现

手柄原来一直亮着（`--ink-4`），复选框却只在悬浮时出现，两者出现时机不同步。
现在手柄**默认 `opacity: 0`**，与复选框用**同一条过渡、同一个时长**淡入 ——
实测过渡中途两者进度差为 0。手柄仍然占着那 16px（`opacity` 而不是 `display`），
出现时不会把姓名挤动。

### 2. 手柄拖动 = 调整这一行的位置（这一条带了一次 Schema 变更）

第八轮我把它做成「连续选中若干行」，理由是「成员顺序由服务端决定，界面上能拖、
刷新就回去的排序是假功能」。用户这次明确要求手柄去调行位置，于是把顺序**真的**做出来：

- **`member_profiles.sort_order` + 前向迁移**：迁移里按「加入时间倒序」把现有行逐行回填
  成 `0..n-1`，所以升级后列表位置与升级前**逐行一致**。新建成员默认 0，与队首并列时用
  `created_at desc` 兜底 —— 「新成员出现在最前面」这条老行为没有丢。
- **`POST /api/v1/admin/members/:id/move`**：`{beforeId: string | null}`，与技能标签 /
  故障分类的 `move` 同一套落点语义与同一套 `movedIds` 算法。一次拖动**只写一次库、
  一条审计**（`member.moved`）；落点没变则幂等成功、不写审计。
- **服务端把整份顺序重排成稠密 `0..n-1`**：新建成员的序号默认是 0、与已有行重复，
  只交换两行的序号在重复值下会「看起来没反应」（`reorder.ts` 里记过同一个坑）。
- **拖动复用 `useRowDragSort`**（AGENTS 要求「列表顺序调整统一用它」）：整行只有手柄
  `draggable`，落点按目标行的上 / 下半判断，指示线是绝对定位伪元素。
  选择一段仍用 `Shift` 点击；「拖」这个手势只留一种含义。
- **键盘 / 触屏路径**：成员表没有操作列（第七轮撤掉了），没有 ↑↓ 按钮可放，
  于是给手柄加了 `role="button"` / `tabIndex` 与 ↑ ↓ 方向键（实测 ↑ 把第 4 行移到第 3 行）。
  技能 / 分类那两个表已经有 ↑↓ 按钮，所以这条键盘支持是**可选**的（`keyboardProps`），
  没有挂到它们身上。

### 3. 「查看」全场最多一个

用户看到的场景是：悬浮 A 行点开「查看」→ 关掉窗口 → 悬浮 B 行 → **两个「查看」同时亮着**。
原因是显形条件里写了 `tr:focus-within`：点过的按钮留着焦点，就一直亮。
现在改成三条规则配合：
`tbody:hover tr:not(:hover) .admin-peek { opacity: 0 }`（权重 (0,4,2)，刻意压过下面两条）
先把非悬浮行的收起，`tr:hover .admin-peek` 显示悬浮行，`.admin-peek:focus-visible`
只在键盘焦点落在**按钮自己**身上时显形。
实测：点过查看再悬浮另一行 → 全场 1 个；指针离开 → 最多剩键盘焦点那 1 个；
在空白处点一下 → 0 个。

### 4. 拖动排序：松手即到位 + 勾选多行整块拖动

两条反馈：「拖动不是立即响应修改的」「多个选中后无法一起拖动」。

**松手即到位（乐观更新）**：原来松手后要等 `POST /move` 往返 + `reload()` 重新取列表，
行才「顿一下」挪到位。现在排序规则收进 `src/lib/list-order.ts` 的纯函数，
**客户端与服务端共用同一份**（两边各写一套必然出现「松手后跳一下再弹回去」），
松手先按它改本地顺序、再发请求；失败回滚 + 报错。成功后**不再重取列表** ——
服务端写的就是同一套规则算出来的顺序。实测：松手到 DOM 顺序更新 **≈155ms**
且发生在接口响应之前。三个可拖动的列表（成员 / 技能 / 分类）都换成了这套手感。

**整块拖动**：`POST /api/v1/admin/members/:id/move` 换成
`POST /api/v1/admin/members/move {memberIds, beforeId}`（1–50 位，支持单行与多行，
所以只有这一个入口），块内保持原有先后，服务端一次写库、一条审计
（`member.moved` 的 `after` 带 `memberIds`）。界面侧的关键一条是
**落点解析跳过被移动的那几行**：勾选三行后拖其中一行，鼠标必然先掠过这三行自己，
不跳过就会解析成「插到自己前面」= 原地不动，用户看到的就是「拖不动」。
拖动中整块标 `is-dragging`。

**本轮验证**：`pnpm lint` 0 error；`pnpm test` 233 项（137 通过 / 96 跳过 / 0 失败，
新增 3 项纯函数测试：整块移动 / `movingRowIds` / `applyOrder`）；集成测试（独立测试库）
12 项全通过（成员拖动排序那条补了「三行整块移动 + 幂等不写审计」）；
浏览器断言 **15 项全通过**：落点提示线、松手 155ms 内顺序已变、DOM 变更早于接口响应、
接口返回后顺序不被重置、刷新后保持、勾选 3 行整块移动且内部先后不变、
整块 `is-dragging`、请求体恰好是选中集合、未知 id 404 且界面不受影响；console 无报错。

### 4. 密码长度策略：12 位 → 6 位，并收敛成一份

用户反馈「你给的密码 123456 会被前端拦住」。查下来不只是数字问题，而是**策略被抄了三份**：
登录表单的 `minLength`、改密表单的 `minLength` + 提示语、邀请码注册表单的 `minLength`、

其中最糟的一处是**登录表单**：登录是「校验密码」而不是「设置密码」，写死 12 位下限的后果

**修复**：

- 新增 `src/lib/security/password-policy.ts` 作为**唯一来源**（`PASSWORD_MIN_LENGTH = 6`、
  `PASSWORD_MAX_LENGTH = 128`、`isPasswordLengthValid`、`passwordLengthMessage`），

- 登录表单**去掉 `minLength`**（保留 `required` 与 128 上限），长度规则只在设置 / 修改密码处生效。
- 改密提示语也从常量拼出来（`密码长度为 6–128 个字符…`），不再各写一份数字。
- 任务书 §7.1「密码长度 12–128」同步改为 6–128，并记下这次下调的理由与补偿措施
  （登录节流：同一 QQ + IP 15 分钟内 5 次失败即锁定）。

**新增回归测试**（`tests/unit/password-policy.test.ts` 3 项）：边界值（5 拒 / 6 过 / 128 过 / 129 拒）、
**短口令能真正落库并校验通过**（`hashPassword("123456")` 不再抛错）、
以及一条源码守卫 —— 剥掉注释后扫描 `src/`，任何文件里再出现写死的 12 位密码边界即失败
（这次事故的根因就是「数字抄了三份」，光测边界值挡不住下一次）。

服务端边界另有一条集成测试（独立测试库）：邀请码注册用 5 位口令 → `VALIDATION_FAILED`，
用 6 位 → 兑换成功**并能真的登录**。

## 第十轮验收修复（列宽拖拽重做 / 长按拖动 / 行首并进首列 / 行高与对齐）

第九轮之后提了六条，其中三条是「上一轮说修好了、其实没好」——所以这一轮先把
**拖拽的几何**量清楚，再动手。

### 1. 列宽拖拽：竖线严格跟随指针（第三次修，这次量了数据）

先把上一版的真实行为量了一遍（1440px，默认列宽，用 CDP 逐帧采样），结果说明
「按指针绝对位置算」并不够：

```text
拖「技能标签」右边界 +120px：
  px=791 目标列[430→674] 宽=244  上一列(成员) 宽=45
拖「成员」右边界 +120px：
  px=667 目标列[385→670] 宽=285  tableW=1079→1199（表格被撑出容器，出现横向滚动条）
拖「维修记录」右边界 −80px：
  px=1325 目标列[1338→1408] 宽=70  右边缘与竖线一动没动
```

即：那一列的**宽度**确实跟着指针变了，但它的**右边缘（也就是竖线）纹丝不动** ——
差额被浏览器塞给了没写死宽度的那一列（成员列从 165px 被压到 45px），
用户看到的是「我拖了半天线不动、列却变形得厉害」，所以判定为「比例被数倍放大」。
拖吸附列更糟：直接让表格总宽涨到容器外。

**这一轮把模型定成 Excel 那一套**：竖线跟着指针走，**它右边的列整体平移**，
差额由**最后一列**吸收，总宽恒等于容器宽。于是 `新宽度 = 指针位置 − 该列左边缘`
（左边缘在拖动中不变）就是唯一真相，行程 = 最后一列宽 − 最小宽（默认 102px）。
中间还试过一版「相邻两列对冲」（左 +Δ、右 −Δ）：方向对了但**行程只有 44px**
（右邻已经到 48px 下限），照样会觉得拖不动，所以只留下了「最后一列吸收」这一版。

配套三处改动：

- **拖动期间不重渲染整张表**：`pointermove` 只手动改 `<col>` 与竖线的行内样式，
  `pointerup` 才落到 state 与 `localStorage`（用户反馈「拉动特别卡」）。
  实测：拖动 12 帧期间 `tbody` 的 `MutationObserver` 计数 **0**。
- **竖线位置改由列宽累加算出**，不再量 DOM：总宽恒定时两者等价，但省掉了
  `ResizeObserver` + `useLayoutEffect` 的来回测量。
- **首屏按默认列宽渲染**：顺手抓到一个自己写出来的 bug —— 去掉 `<col>` 的 `style` 之后
  宽度只在拖动时写进 DOM，首屏 9 列被 `table-layout: fixed` **均分**成 120px。
  现在宽度由 React 渲染，拖动时再由 hook 直接改属性。

同时修掉三处「表格明明铺满容器、却多出横向滚动」的溢出（都不在表格本体上）：
表头文字（「联系方式」四个字 58px 挤进 54px 的列）、`.admin-contacts` 的子项、
以及标签行的行内盒。做法是 `th`、`.admin-contacts` / `.admin-tags` 及其子项
都允许收缩并自己裁（`overflow: hidden` + `text-overflow: ellipsis`）。

### 2. 行首：并进首列 + 长按才拖动

- **行首不再独占一列**：六点手柄、序号 / 复选框并进「成员」单元格，
  复选框右边缘到姓名只剩一个固定间距（实测 **9.2px**，之前是 25px）。
  省下的 56px 全部给姓名列（默认 221px）。
- **长按约 260ms 才进入拖动**（用户明确要求「那个六面骰 icon 长按是拖动」）。
  按下去就拖的话，想点复选框、想选文字、想滚动列表都会误触发；蓄力期间移动超过 6px 即取消，
  蓄力完成时手柄点亮（`is-armed`）作为「可以拖了」的确认。
- **勾选后取消勾选要退回序号**：显形条件从 `tr:focus-within` 改成 `tr:has(:focus-visible)` ——
  鼠标点完复选框焦点留在 input 上，`:focus-within` 会把复选框一直钉着（实测反馈）；
  `:focus-visible` 只在键盘操作时为真。
- **复选框必须显式居中**：它是替换元素，`inset: 0` 配 `.admin-check` 的固定宽高会被
  浏览器当成「左上定位、右边忽略」，于是压在盒子左上角；`margin: auto` 才两轴居中。

### 3. 单元格对齐与行高

- **一律左对齐 + 垂直居中**：撤掉「加入时间 / 维修记录」的右对齐（用户反馈
  「加入时间为什么擅自改成右对齐，单元格都是左对齐 + 居中好看」），
  `.admin-table__num` 这条规则随之删除。
- **行高唯一**：实测 40 行里混着 29px 与 27px。原因不是文案，而是**标签比行框高** ——

  正文行框只有 19.5px（13px × 1.5）。修法是让行框稳压标签一头
  （`line-height: 1.75` = 22.75px），并把标签自己的 `line-height` 钉回 1.5
  （它是继承来的，行框一改高它跟着长，永远追不上；压 `min-height` 也没用 ——
  标签的高度是内容 + 描边撑出来的）。实测 40 行全部 30.33px
  （首 / 末行 29.83px：`border-collapse` 把共享的 1px 描边对半分，差 0.5px）。

### 2. 行首：六点手柄 + 序号（悬浮变复选框）

- 行首那一列现在是 `[⠿][1]`：左边拖动手柄，右边**序号**；指针进入这一行（或键盘焦点
  落进来）时序号换成**复选框**。两者同尺寸同位置，用 `opacity` 互换，行高列宽都不动。
  已选中的行始终显示复选框，勾选状态不会被藏起来。

  要真的可排序得先有持久化的顺序字段，那是另一个变更。

### 3. 竖线改成 Excel 式全局竖线，并修掉拖动比例失真

- **贯穿整表**：竖线不再是表头里的小柄，而是在表格之上铺一层 `.admin-colgrid` 覆盖层，

- **比例失真**（用户反馈「拖动的实际距离是真实距离的数倍」）：原因是宽度按**位移增量**算

  表格宽度与列宽之和不等时，浏览器会再做一次分配 —— 位移就会被成倍放大。

- 表格元素改用**回调 ref + state** 保存：首屏数据没回来时表格还没进 DOM，普通 ref 会让
  量尺度的 effect 在挂载那一刻拿到 null、之后再也不量，竖线一条都不显示（实测踩到）。

原「操作」列放着「详情 / 重置密码」两个按钮，占约 140px。现在：

- 详情入口变成**悬浮整行时出现在首列右端**的 `.admin-peek` 小框（文案「查看」）。

- **`table-layout: fixed` 是前提**：auto 布局会按内容重算宽度，用户拖出来的数字下一帧就被改回去。
- **分隔条必须完全落在本列之内**：第一版骑在列边界（`inset-inline-end: -0.25rem`），

## 第七轮验收修复（切页抖动 / 后台页脚 / 新增成员弹层 / 表格装信息）

第六轮之后又提了五条，外加一条流程要求（少截图、清临时文件，已写进 `AGENTS.md` 第 8 节）。

### 1. 切页「抖一下」：三个不同来源的位移

用户描述是「Admin Console 上方的空白高度突然小了一下，然后恢复」。用 CDP 在一次
客户端导航期间每 25ms 采样一次几何（`nav` / `brand` / `content` / `docH` / 滚动条宽度），
复现出**三个**叠加的来源：

| 来源                                                                    | 现象                                                                                                               | 修复                                                                   |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| `app/admin/loading.tsx` 比真实页面少两层外壳（`Section` / `Container`） | 骨架内容比真实页面高 16px、左边少一层内边距，载荷到达时整页跳一格                                                  | 骨架改成与页面**逐层同构**                                             |
| `.admin-nav` 的 `inset-block-start: var(--s-4)`                         | sticky 位移受包含块高度限制：页面高时被顶到 16px，页面矮（骨架那一屏、或只有几行的短页面）时夹回 0 → 侧栏上跳 16px | 改成 `inset-block-start: 0`，留白由侧栏自身 `padding-block-start` 提供 |
| 滚动条出现 / 消失（页面高度在 1715px 与 1000px 之间切换）               | 布局宽度变 15px，整页横向抖                                                                                        | `html { scrollbar-gutter: stable }`                                    |

修复后同一段导航：`nav top` 恒为 0、`brand top` 恒为 12、内容起点恒为 16、
`body` 宽度恒定（探针断言 5 项全通过）。

### 2. 后台不显示页脚

页脚的落款、英文名、年份、文档来源与备案号属于公开站点，在后台既没用又占高度。
**修复**：`body:has(.admin-shell) .footer { display: none }`。用 `:has()` 而不是在根 layout
判断路由 —— 根 layout 渲染 `<Footer/>` 时并不知道当前路由，`：has()` 表达的正是

### 3. 新增成员：从「表格下面追加面板」改成弹层

原实现点「新增成员」是在整张表**下面**插入一个卡片，而表格有一两千像素高 ——
用户看不到任何变化，原话是「我甚至前面很长一段时间都以为这个功能出bug了」。
**修复**：改用 `AdminModal`（窗口出现在视线中央，页面零位移，探针断言开窗前后的

创建成功后原代码立刻 `setCreating(false)` 把表单卸载，**初始密码从未被看到过**。
现在窗口不自动关闭，表单切换成结果视图（已创建 + 一次性初始密码 + 「完成」）。

### 4. 顺带发现并修掉：重复 QQ 会静默改掉别人的资料

探针复用时用同一个 QQ 建了两次，第二次返回 **201 且没有初始密码**。原因是
`ensureMemberProfile` 会复用已有档案并覆盖 `realName` / `studentId` / `className`，
而 `setInitialPassword` 因为已有密码直接返回 false。
**修复**：`memberService.create` 在目标 QQ / 手机号已属于某位成员时抛 409
`ACCOUNT_IDENTITY_CONFLICT`，错误信息带上那位成员的名字；要改资料请走成员详情的编辑。
（探针断言：第二次创建 409、原成员姓名未被改。）

调研见下节。这一轮先落地「零/低成本」的三件事：

### 飞书多维表格调研（子任务产出，用于后续设计）

调研报告见 `docs/飞书多维表格调研.md`。结论摘要：

## 第六轮验收修复（同步批量工具 / 拖动排序 / 页脚与去重）

第五轮之后又提了四条：「其他有批量操作的界面也应该同步」「技能标签用拖动调整」
「评论管理的两个总数重复了」「页脚太高、那句话要一行显示」。

### 1. 批量工具只有一个实现（`AdminBatchTools`）

成员管理与维修审核是后台里仅有的两处批量操作。第四轮把它们都搬进表格顶栏时是各写一遍的，
于是同一个东西长出了两种样子：成员管理是「勾选框 + 批量动作 + 取消选择」，
维修审核中间还插了个退回原因输入框，顶栏比成员管理高一截。
**修复**：抽出 `components/admin/AdminBatchTools.tsx`，结构固定为
`[全选] [已选择 N 项 / 未选择记录] │ [批量动作…] [取消选择]`，两处只传自己的动作按钮。
**批量退回的原因改成弹层**（标题「退回原因」，副标题写「已选择 N 条记录」，
没填原因时确认按钮置灰）—— 需要额外输入的批量动作不该占着顶栏。
顺带把维修审核的筛选栏从两行收回一行：6 个字段的 `flex-basis` 从 `10rem` 收到 `8.25rem`
（关键字 `16rem → 12rem`），实测字段宽度 `198/135×5`、一行放得下，
成员管理与维修审核的筛选栏终于长得一样。

### 2. 技能标签 / 故障分类：拖动排序

原先每行两个「↑ ↓」按钮，一次只能挪一格。
**修复**：行首加拖动手柄（`Icon` 新增 `grip`：两列三点，唯一用实心圆的图标），
拖动落点按目标行的**上半 / 下半**决定插到它之前还是之后 —— 只判断「悬停在哪一行」
就永远拖不到列表末尾。三条细节都是必须的：

- **只有手柄 `draggable`**，整行不可拖：整行可拖会让表格里的文字选不中（学号、备注要能复制）。
- **指示线用绝对定位伪元素**：`border-block-start` 会把行高撑大 2px，拖动时整张表跟着跳；
  `box-shadow` 是设计基准的禁止项。
- **拖动项记在 ref 里，不只用 state**：`dragstart` 里 `setState` 之后 React 要到下一帧才把
  新闭包交给事件处理器；真实拖动时两次事件之间隔着鼠标移动，状态早已提交，所以平时看不出问题，
  但同一帧里连发 `dragstart`/`dragover`（自动化验证就是这样）时整条链会静默失效。
  落点判断是逻辑，逻辑用 ref；`draggingId` 的 state 只负责样式。

服务端新增 `POST /api/v1/admin/skills/:id/move` 与
`POST /api/v1/admin/repair-categories/:id/move`（`{beforeId: string|null}`，`null` = 末尾）：
拖动会跨越任意格数，用「上移 / 下移」模拟要发 N 次请求、写 N 条审计，
所以 `move` 一次算出最终顺序、一次写库、一条审计（`skill.moved` / `repair.category.moved`）。
与 `reorder` 共用 `movedIds` / `reorderedIds`，都写稠密序号、都在落点未变时幂等成功。
**键盘与触屏路径保留 ↑ ↓**：HTML5 拖放在触屏上根本不触发。

### 3. 列表末尾不再重复总数

评论管理顶栏右侧写着「共 3 条评论」，表格下面又来一句「共 3 条」。
`adminShared.listEnd.all` 从 `共 {total} 条` 改成 **「已全部加载」**，
`AdminListEnd` 在总数 0 时直接不渲染（表格里已经写着「暂无数据」）。六个列表一起生效。

### 4. 页脚：压缩高度 + 免责说明一行

页脚是页面结束的落款，不是内容区：原先上下 `--s-6 / --s-7`、三段之间各 `--s-4`，
整块接近 240px。**修复**：`padding-block` 改 `--s-4 / --s-5`，两段说明的
`margin/padding-top` 收 `--s-3`，`line-height` 1.8 → 1.65，实测 **149px**。
`.footer__note` 的 `max-width: 78ch` 直接删掉 —— 那句话是一句完整的话，
按 `ch` 限宽会在一行只差二三十像素时硬折成两行；宽度够就一行读完，不够再自然换行
（1440px 实测 1 行 / 1231px 宽）。

- `pnpm lint` 0 error；`pnpm test` 221 项（128 通过 / 93 跳过 / 0 失败）
- 集成测试（真实 GreatSQL，`RUN_DB_TESTS=1`）：批次 2 的 10 项全通过，

- 浏览器探针 **28 项全通过**（`dsh-m6b-round6.mjs`）：页脚 4 项、评论去重 3 项、

### 顺带记录

- 探针第一版把「拖动」的三段事件放在同一个 JS 帧里发，全部静默失败：这正是上面那条
  「状态要等渲染」的坑，也说明 **hook 里用 ref 记录拖动项**不只是洁癖。修完 hook 之后，
  探针仍按真实时序分三段派发（`dragstart` → `dragover` → `drop`），两边都不依赖运气。
- 判定「页脚那句话是不是一行」不能数 `Range.getClientRects()` 的个数：一个 `<a>` 会把

  卡片布局里的 `.admin-table td { display: grid }` 权重更高（类 + 类型 > 单个类名），
  必须写成 `.admin-table td.admin-table__grip`。截图里一眼就能看出来，说明**改完要看图**。
- 评论列表状态列里的「正常」原本硬编码在组件里，本轮一并收进 `config/admin.ts`

## 第五轮验收修复（密度 / 邮箱式列表 / 页脚）

第四轮改完后再看一遍，提出「空间利用率不够、控件太大」「批量组件应该像 QQ 邮箱那样放在表格顶栏」
「上一页下一页改成无限下翻」「页脚跑到屏幕中间了」四条。逐条处理。

### 1. 页脚浮到屏幕中间（内容不足一屏时）

短页面（例如只有 8 行分类的 `/admin/categories`）上，页脚紧跟着内容，停在屏幕中部。
原因很直接：`body` 只是普通块级流，`<main>` 没有最小高度，内容多高页面就多高。
**修复**：`body` 改为纵向 flex + `min-block-size: 100dvh`，`main { flex: 1 0 auto }` ——
正文吃掉剩余高度，页脚自然贴底。固定定位的索引栏 / 顶栏 / 背景网格不受影响。
实测 `/admin/categories`：页脚 `bottom` = 视口底部（`atBottom: true`），页面高度 = 视口高度。

### 2. 空间利用率：把官网那套留白从后台摘掉

后台页面复用了官网的 `<Section variant="page-head">`，于是连官网首屏的留白策略一起继承了。
1440px 实测（修复前）：

```
section.admin-workspace   padding-block 100px          ← 官网页头是给巨型标题 + 水印用的
.admin-workspace > .shell padding-inline 60.48px       ← 官网容器的居中 + 侧边距 + max-width
.admin-workspace__content 宽 976px（可用 1097px）
```

**修复**（只在 ≥1100px 生效）：页头 `padding-block` 收到 `--s-4`；`.admin-workspace > .shell`
取消 `max-width` 与侧边距；右侧留 `--s-4` 别顶到视口边。修复后：

```
section.admin-workspace   padding-block 16px
.admin-workspace__content 宽 1081px
```

内容宽度 +11%，页面顶部少掉 84px 空白。

### 3. 密度：控件与行高按数据界面重做

| 元素            | 官网尺寸                           | 后台（≥760px）                      |
| --------------- | ---------------------------------- | ----------------------------------- |
| `.btn`          | 46px 高 / `padding 0.95rem 1.6rem` | 24px 高 / `padding 0.15rem 0.55rem` |
| `.field__input` | 46px 高 / 16px 字                  | 28px 高 / 13px 字                   |
| 表格单元格      | `padding 0.85rem`、14px 字         | `padding 0.2rem`、13px 字           |
| 表格行高        | ~62px                              | ~34px                               |
| 页头标题        | `--t-xl`（最大 2.75rem）           | `--t-lg`（最大 1.5rem）             |
| `.admin-panel`  | `padding clamp(1.25–1.75rem)`      | `padding --s-4`、`gap --s-3`        |

**只在 ≥760px 生效**：窄屏仍然是手指操作，46px 的触控面积要保留；
`.field__input` 的 16px 还兼着「iOS Safari 聚焦时不放大整页」这个作用。

**列宽**也一并收：原先 `table-layout: auto` 把富余宽度平均分给每一列，窄列（状态、角色、操作）
之间因此出现大片空白。现在只有标注 `admin-table__grow` 的内容列吸收富余宽度，其余按内容收窄。
实测成员表列宽：成员 384（内容列）/ 学号 84 / 班级 103 / 角色 54 / 状态 42 / 已通过维修 78 /
联系方式 153 / 操作 148。

> 踩坑记录：先用「其它列 `width: 1%`」的写法，结果容器不够宽时浏览器把窄列压到比内容还窄，
> 行内的 flex 组（`.admin-actions` / `.admin-contacts`）换行，**行高反而从 34px 涨到 61px**。
> 改成「内容列 `width: 100%`」才稳定。另外 `white-space: nowrap` 管不到 flex 容器 ——
> 单元格里的横排组要显式 `flex-wrap: nowrap`，否则「详情 / 重置密码」会被折成两行。

### 4. 批量组件移到列表顶栏（QQ 邮箱式）

按反馈把「已选择 N 名成员 / 批量启用 / 批量禁用 / 取消选择」从浮条改成**列表顶栏**：

  表格…

- 新增 `AdminListToolbar`：左侧选择状态与批量动作，右侧总数。**常驻**、未选中时按钮置灰 ——

  「交互不得夺走操控权」。同时「选中之后能做什么」在操作前就看得见。

### 6. 顺带修掉的 hydration 警告

改完外壳后 `/admin` 首页在浏览器里报 React hydration 不匹配（公开页不会）。定位：
`SiteEffects` 给 `.reveal` 元素直接加 `is-in`，DOM 与 React 的 vdom 分叉；只要路由器之后
重渲染到这棵子树就会报。触发条件正是导航预取 —— 10 个链接挂载即预取，预取完成会让路由器
重渲染当前页。
**修复**：(a) 导航预取改成**按意图触发**（悬停 / 聚焦 `router.prefetch`），既省掉 10 个
无用请求，也不再让路由器在 hydration 后立刻重渲染；(b) 后台不做进场揭示 ——
`.reveal` 在 `.admin-shell` 内被 CSS 中性化，`SiteEffects` 也跳过 `.admin-shell` 里的元素，
两边一致，分叉消失。实测 6 个页面 × 连续导航：警告为 0。

## 遗留治理（本次踩到的两个坑，都会影响后续模块）

### 1. `pnpm test:db` 会清空数据库

`tests/integration/m0-database.test.ts:38-49` 使用的是**无 `where` 的全表 `deleteMany()`**
（`m3-member-dashboard.test.ts:42` 的注释也写明了「M2 的 `before()` 会全表 `deleteMany()`
（含 users / member_profiles）」）。因此对 `.env` 指向的开发库执行 `pnpm test:db`
**会删掉开发库里的全部用户、成员与业务数据**。

本次执行 `pnpm test:db` 时确实清空了开发库（含开发者自己 bootstrap 的管理员、一条可用邀请码
以及一次真实的邀请码注册记录）。已用只新增的引导脚本把「开发管理员 + 邀请码」补回，未再删除
任何数据。**强烈建议把集成测试指向独立数据库**（例如另一个 schema `zafu_pchospital_test`，
或独立实例），这也是 M3 报告中「本机测试数据库为独立实例（端口 3308）」的做法。

### 2. 同一个 checkout 只能有一个进程写 `.next`

`.next/` 是共享目录，因此 `next build`（`pnpm build` / `pnpm build:site`）与 `next dev`
**不能同时跑**，两个 `next dev` 也不能同时跑。混用会让 `.next` 里的路由清单与 chunk 互相覆盖，
症状相当隐蔽：

- 页面 HTML 返回 **200**，但它引用的 chunk 返回 **404** → React 从未 hydrate → 表单提交退化成
  原生 GET 提交，看起来就是「登录按钮没反应、输入什么都在原地打转」，而同一时刻用 curl 直连
  API 却是正常的 200；
- 更严重时**存在的路由会返回 404**（本次出现过 `/api/v1/auth/login` 404），此时重启进程也不够，
  必须先 `rm -rf .next` 再起。

本次验证过程中两种表现都踩到了。结论：**要在改完代码后跑构建自检，先停掉 dev server；
必须同时保留 dev server 时，先 `rm -rf .next`，并且只留一个 dev server。**

### 3. `pnpm test:db` 原本无法加载 `.env`

`test:db` 的脚本此前是 `tsx --test …`，不加载 `.env`，因此在本机直接跑会以
「缺少服务端环境变量：DATABASE_URL, AUTH_SECRET, …」全部失败（既有 84 项集成测试同样如此）。
本次给该脚本加上 `--env-file=.env`：Node 的语义是**环境变量优先于文件**，所以显式导出的
变量（例如指向独立测试库的 `DATABASE_URL`）仍然生效，不会覆盖开发者的设置。
