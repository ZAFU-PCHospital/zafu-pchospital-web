# 后台表格内核（AdminTable）

> 状态：**P0（内核）+ P1（成员表接入、服务端排序）+ P2（表头排序界面、就地编辑）已落地**，其余五个后台面板
> 待迁移。本文说明它为什么存在、边界在哪、以及怎么把下一个列表迁进来。
> 改动依据：M6 第九轮验收反馈「不能像多维表格一样统一管理所有表，现在的设计很割裂分离，
> 毫无 openness 和易用性」。

## 1. 要解决的问题

M6 的六个后台列表（成员 / 技能 / 分类 / 评论 / 邀请码 / 招募 / 审计）各自维护
**三份彼此平行的列定义**：

| 位置     | 例子                                                             |
| -------- | ---------------------------------------------------------------- |
| 列宽数组 | `MemberAdminPanel` 的 `COLUMNS`（`useColumnResize` 用）          |
| 表头     | 同一文件里的九个 `<th>`                                          |
| 单元格   | 同一文件 `tbody` 里的九个 `<td>`（含各自的空值、截断、徽标规则） |

三份定义一旦漂移，就会出现「拖列宽拖错列」「表头与内容对不上」；而**加一张新表 =
再抄一遍 400–700 行**（六个面板合计约 5900 行）。这就是验收里说的「割裂」。

内核把这层收敛掉：**一张表 = 一份 `TableViewSpec`**，其余由 `<AdminTable>` 提供。

## 3. 四层设计

```text
字段层   FieldSpec        一列：key / label / kind / 宽度 / render / 类名 / 可排序性
视图层   TableViewSpec    一张表：id / title / rowKey / fields
查询层   ListQuery        page / pageSize / query / sort        ← 服务端与客户端共用
渲染层   <AdminTable>     把 spec 渲染成 .admin-table 标记 + 表头排序入口
```

**三条刻意的边界：**

1. **内核不取数。** 数据由页面用 `useAdminList` 取回后传入 —— `AGENTS.md` §2 要求
   「取数与自动加载下一页统一用 `useAdminList` + `AdminListEnd`，不要再写第二份分页逻辑」，
   内核若自己包一层取数，就成了第三份。`<AdminTable>` 也就不渲染 `AdminListEnd`。
2. **内核不持有排序状态。** 排序会改变服务端返回的行集合，因此它必须与 `fetchPage`
   待在同一个作用域（页面）里。内核只把点击翻译成新规则（`cycleSortRule`）再回调。
3. **内核不猜类名。** `headClassName` / `cellClassName` 逐列由 spec 给出，迁移时照抄现状，
   从而保证「迁移前后 DOM 一致」——这是像素级不回归的前提。

## 4. 排序约定

查询参数：`sort=<field>:<asc|desc>[,<field>:<asc|desc>]…`

- 字段必须在白名单（`sortableFields(spec)`）内，否则 `VALIDATION_FAILED`
  （与 `member-http.ts` 的 `oneOf` 同一原则：**绝不把用户字符串透传给查询**）；
- 方向省略按 `asc`；同一字段重复只保留第一条；
- 最多 3 个字段（`MAX_SORT_RULES`），**超限即拒绝，不静默截断**
  （与导出「超限即拒绝」同一口径）；
- 表头点击是 **未排序 → 升序 → 降序 → 未排序** 三态：服务端默认顺序是列表的正常状态
  （成员表默认按加入时间倒序），必须有入口退回去；
- **默认排序属于服务端**（`parseListQuery` 的 `defaultSort`），不能由前端拼进 URL ——
  否则第一次 GET 与后续 GET 口径不一致，无限下翻会出现重复行或漏行。

客户端用 `listQueryParams` 拼参数、服务端用 `parseListQuery` 解析参数，两边共用同一份规则，
因此不会出现「界面能点、后端报 400」。这条一致性由单测直接覆盖。

## 5. 怎么迁移一张表（成员表已完成，其余照此办理）

前置条件：**该面板的列相关改动已提交**。内核不碰别人正在改的文件。

1. 为这张表写一份 spec（`render` 逐列照抄现有 `<td>` 内容，类名照抄现有 `<th>` / `<td>`）。
   三条要逐字照抄、不要顺手「优化」的东西写在 `member-table-spec.tsx` 顶部：
   列 id 不能改（列宽偏好按 id 存 `localStorage`）、该右对齐但当前没右对齐的列要显式
   `numeric: false`、聚合列与关联列显式 `sortable: false`；
   行首那种**没有可见表头**的列（拖动 / 选择）：`label: ""`，需要列名时写
   `headLabel`（渲染成 `sr-only`，不参与布局，因此像素不动）；没有字段名的列
   内核**不写** `data-label`（空属性会被卡片模式读成空字段名）；
2. 页面把 `<div className="admin-table-wrap">…<table>` 那段换成 `<AdminTable>`，
   并把 `useColumnResize` 的 `widths` / `colRefs` / `tableRef` 透传进去；
   覆盖层（如成员表的 `.admin-colgrid`）走 `overlay`；
3. 单元格需要的运行时值（行首选择控件、跳详情的回调）走 `renderContext`，
   **不要**把 spec 做成工厂函数 —— spec 必须保持模块级常量，否则列宽 hook 的依赖会抖动；
4. 排序先不开（不传 `onSortChange`）：此时 DOM 与迁移前等价，先跑
   `tests/unit/admin-table-render.test.ts` 那套契约测试确认零回归；
5. 后端接通 `sort` 参数后（见第 6 节），再传 `onSortChange` 打开表头排序。

**迁移成员表的实际收益**：面板 534 行 → 365 行，`COLUMNS` / `<th>` / `<td>` 三份列定义
合成一份 `memberTableSpec`。

**逃生口：整行接管（`renderRow`）**。遇到「一行里有几个格子不属于逐列模型」的情况时用它，
而不是把 spec 改成工厂函数、也不是在 spec 里塞一个巨大的 `render`：
邀请码列表的「调整策略」把中间四列合成一个 `colSpan` 表单（服务端一次 PATCH 提交三个字段），
逐列渲染表达不了，拆成三个各自编辑的单元格又会把一次提交拆成三次。
`renderRow` 返回节点时这一行完全由调用方渲染，**`<tr>` 与列宽仍由内核负责**
（`data-row-id` / `rowProps` / `<colgroup>` 照旧）；返回 `null` 就走常规渲染。
它只该用来表达这种「跨列的一行」，不要用它绕过 spec。

### 5.1 与「拖动排序」的关系（成员表特有）

成员表有**两套顺序**：管理员拖出来的持久顺序（`MemberProfile.sortOrder`，服务端默认顺序）
与用户点表头产生的排序。两者不能同时生效：

- 不带 `sort` 时，服务端按 `[sortOrder asc, createdAt desc, id desc]` 返回 —— 拖动结果可见；
- 带 `sort` 时，用户的选择优先，**此时界面上不该再提供拖动**（否则「拖了但顺序不变」）。
  这一条需要面板在排序激活时收起拖动手柄，属未完成项。

## 6. 服务端排序（成员表已完成，其余列表照此办理）

表头排序**不是纯前端功能**：对当前这一页的 20 条记录排序是假排序。成员表的链路是：

```text
member-http.ts     sortRules(params.get("sort"), MEMBER_SORTABLE)   ← 白名单 + 方向 + 去重 + 上限
member-service.ts  原样透传 MemberListInput（不重新解释参数）
member-repository  orderBy: memberOrderBy(input.sort)               ← 映射到列 + 补 tiebreaker
contracts.ts       MemberListInput.sort?: SortRule[]
docs/contracts     「通用列表查询参数」一节 + 该端点的白名单
```

两条硬约束：

1. **永远保留 tiebreaker**：主排序键重复（同名成员、同秒创建）时名次不确定，
   `skip` / `take` 分页就会读重或漏行 —— 而列表是无限下翻的连续流，重复行用户直接看得见。
   实测提醒：把 tiebreaker 去掉后**集成测试仍是绿的**（小表上 InnoDB 恰好稳定），
   所以真正守住它的是单元测试，集成用例只是端到端护栏；
2. **白名单前端表头与后端校验共用一份**（`sortableFields(spec)` ↔ `MEMBER_SORTABLE`），
   不会出现「界面能点、后端 400」。

其余列表接入时按同一形状复制即可，注意各列表的**默认顺序**不同
（维修按维修日期倒序、审计按创建时间倒序…），默认顺序属于服务端。

## 7. 就地编辑（P2，已落地）

界面上：可编辑的单元格包成一个按钮（点即进入编辑），编辑态是一个输入框。

| 交互     | 行为                                      | 为什么                                                       |
| -------- | ----------------------------------------- | ------------------------------------------------------------ |
| 单击     | 进入编辑态，光标落在输入框（`autoFocus`） | 「能就地编辑」的入口必须只有一个动作，双击在后台表格里会误触 |
| `Enter`  | 提交                                      | 键盘用户不必找保存按钮                                       |
| `Esc`    | 取消                                      | 改坏了要有一条不问任何问题的退路                             |
| 失焦     | **值变过才提交**，没变就只是关闭          | 没变还发请求 = 一次多余的写 + 一条多余的审计                 |
| 提交失败 | 退出编辑态 + 页面浮层提示一次             | 留一个改不动的输入框更糟（用户会以为还能重试成功）           |
| 提交成功 | **单元格当场换成服务端返回值**，不弹提示  | 新内容原地替换本身就是反馈，浮层在这里只是噪音               |

**三条不能破的约束：**

1. **零位移**：按钮用 `p-0 text-start` 抵掉 UA 的内边距与居中，输入框把尺寸相关的一切
   清零或继承（字体、行高、内边距、边框），焦点提示只用 `outline`（不参与布局）。
   进入/退出编辑既不改行高也不改列宽；
2. **只开给标量列**：复合单元格（成员表首列）不开 —— 一个单元格里两层东西，
   点进去改哪个说不清（第八轮验收的原话）。这类编辑留在详情窗口；
3. **成功后不整表重取**：整表重取会把无限下翻出来的几页缩回第一页。
   为此 PATCH 必须返回**新的 `version`**（`MemberUpdateView`），界面把它就地合并进那一行；
   否则第二次编辑用旧版本号必然 409。

## 8. 列级筛选（P2 第二半，已落地）

服务端契约（`filter=<field>:<op>:<value>`、运算符、上限）在
`docs/contracts/api-v1.md` 的「通用列表查询参数」一节。这里说界面这一半。

界面上有两处筛选，**分工不同、同时生效**：

|          | 快捷筛选条（`.admin-filters`）         | 列级筛选（本节的弹层）                    |
| -------- | -------------------------------------- | ----------------------------------------- |
| 表达什么 | 最常用的那几件事，各写各的参数         | 任意一列加条件                            |
| 例子     | `query`（跨列关键字）、`status`、`role` | 学号包含 `2023`、加入时间 ≥ `2026-01-01`  |
| 加一列   | 要写解析、写表单                       | 在 `FieldSpec.filter` 里声明一下即可      |
| 放不下   | 关联（`role` 一个成员有多个，不是一列） | 关联列、派生列（脱敏拼接、跨表聚合）      |

三条设计决定：

1. **弹层而不是内联面板**：表格一两千像素高，往上插一块面板会把列表整个顶下去
   （零位移约束）。弹层挂在 `body` 上（`AdminModal`），开关都不动布局；
2. **一条条件一个 `filter` 参数**，不用逗号挤成一个：值是用户输入，可能自带逗号或冒号，
   重复参数交给 `URLSearchParams` 编码，不自己发明转义规则（发明转义规则的下一步一定是
   转义 bug）；
3. **草稿只在「应用」时生效**：弹层里改的是草稿（`src/lib/table/filter-draft.ts`，
   纯函数），中途输入不发请求 —— 每敲一个字符取一次数既是无谓往返，也会让列表在打字
   过程中反复闪。有没填完的条件时「应用」是灰的，并写明为什么：只提交填好的那几条，
   会留下一条「看着生效、其实没提交」的条件。

用户能看见的三件事：

- 入口**常驻**工具栏，不因「有没有条件」出现或消失；计数槽位宽度固定（上限 5 条 =
  一位数），因此数字从空变成 3 时按钮宽度不变，同排按钮不会横移；
- 有条件在生效时按钮换成信号色**描边**（不是填充：填充留给同一排的「新增成员」）；
- 到达上限时「添加条件」是禁用态 + 一句「最多 5 条条件」，而不是点了没反应。

**换条件后回第一页并清空已选**（走 `load()`），与表头排序的门控不同：排序只换顺序，
条件换的是「列表里有哪些成员」——已勾选的那几个可能已经不在结果里，留着做批量操作就是
误伤。用「上一次生效的条件」做闸门，因此挂载时不会多取一次，点开弹层又原样应用也不会白取。

给别的表接入，三步：

```text
1. spec      FieldSpec.filter = { ops, input }（复合列再用 key 指定后端字段名）
2. 服务端    src/features/<域>/<域>-filter-fields.ts   白名单（前端表单与后端校验共用）
             src/features/<域>/<域>-filter.ts          条件 → where，值在这里解释
3. 面板      state + filterParamValues(rules) 拼参数 + 变化门控 + 触发器与弹层各一个
```

第 1 步与第 2 步必须**逐项一致**：多一个运算符就是「点了必然 400」，
少一个就是「后端支持却选不出来」。这条由 `tests/unit/admin-filter-render.test.ts` 守住
（它会点名白名单里还没有界面入口的字段，当前是 `nickname` —— 它跟姓名同一格显示，
用关键字搜索更快）。

## 10. 验收方式

- **断言优先**（`AGENTS.md` §8.1）：能用 CDP 读 DOM 说清的一概不截图；
- 单测覆盖纯函数层：参数解析、白名单拒绝、三态循环、上限、客户端与服务端一致性、
  字段默认对齐与可排序性；
- **迁移的 DOM 等价性用「逐字节对拍」证明，不靠肉眼看截图**：把迁移前那段手写 `<table>`
  的 JSX 原样复制成一个小函数，用 `renderToStaticMarkup` 渲染；同一份数据再渲染内核的
  `<AdminTable>`；两次结果做**原始字符串比较**（`RAW_EQUAL`）。相等就说明列顺序、文案、
  `data-label`、类名、空值占位、`colSpan`、`caption` 一个字符都没动 —— 比截图对拍更严格，
  也更快（截图还要人盯着看两遍）。对拍脚本是一次性的，不入库；入库的是它换来的
  `<panel>-table-render.test.ts` 契约测试（把同一批断言钉住，防将来的漂移）。
  对拍要覆盖**填充态与空态**两边：空态走的是另一条渲染分支（`admin-table__empty`）；
- 迁移每个面板时，另对拍该面板的**同一视图**截图（`shots/` 只在人工确认后更新，
  且图库更新单独成一次提交）。
