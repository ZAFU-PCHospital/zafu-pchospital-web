# M0 基础架构与数据契约开发任务书

> 项目：浙江农林大学电脑医院官网 Phase 2
> 适用对象：多人协作开发者、Codex / Claude Code / Cursor 等 AI Agent
> 数据库：GreatSQL 8.x
> 任务性质：基础设施与公共契约，不交付完整业务页面
> 前置文档：`AGENTS.md`、`docs/design-system.md`、`docs/architecture.md`、`docs/第二期需求分析文档.md`

---

# 1. M0 目标

M0 的目标是先建立 Phase 2 所有模块共同依赖的基础设施和稳定契约，使账号、招募、维修、统计、后台等后续模块可以并行开发而不各自定义数据库与 API 规则。

M0 完成后必须具备：

- GreatSQL 开发环境与应用连接能力
- 版本化 Migration 与幂等 Seed
- 统一 `User / Role / UserRole / MemberProfile` 基础模型
- `JoinApplication / InviteCode / AccountProvision` 等招募领域模型
- 集中的 Enum、公共 Type、API 信封、错误码与分页规范
- 权限校验骨架、审计写入骨架和事务边界
- 可供 M1 及后续模块直接调用的 Repository / Service 接口
- 自动化测试、迁移验证和交付报告模板

M0 的核心结论：

> `User.id` 是统一账户本体；QQ、手机号、密码、未来 QQ/微信 OAuth 都是可绑定身份或凭据。报名记录和邀请码只负责建立成员身份，不得取代 `User`。

# 2. 技术决策

## 2.1 数据库

统一使用 **GreatSQL 8.x**，按 MySQL 8.0 兼容协议连接。GreatSQL 官方文档说明其可作为 MySQL 或 Percona Server for MySQL 的兼容替代；部署时必须固定具体小版本，不使用浮动 `latest`。

数据库基线：

```text
Storage Engine    InnoDB
Character Set     utf8mb4
Collation         由运维在 M0 开工时锁定，全环境一致
Time Zone         数据库会话与应用统一 UTC
Transaction       账号发放、邀请码消费使用显式事务
```

参考：

- [GreatSQL 8.0 用户手册](https://greatsql.cn/docs/8.0.32-27/)

## 2.2 ORM 与版本约束

M0 建议采用 **Prisma ORM 7 的稳定版本**，使用 `provider = "mysql"` 接入 GreatSQL。Prisma 官方支持 MySQL 8.0 和版本化迁移；GreatSQL 以 MySQL 8.0 兼容协议工作，因此该组合可作为项目基线，但必须先在固定 GreatSQL 版本上完成连接、迁移、事务和并发测试。

约束：

- Prisma 版本必须精确锁定在 `pnpm-lock.yaml`，不得使用浮动大版本。
- 在 Prisma 8 的 MySQL 支持正式稳定并完成项目回归前，不升级到 Prisma 8。
- 新增 Prisma 相关运行时/开发依赖只能出现在 M0 PR，并在 PR 中单独说明必要性和包体影响。
- 若验证发现 GreatSQL 与 Prisma Migrate 存在阻塞差异，停止后续 Schema 开发，提交兼容性记录，由架构负责人决定改用版本化 SQL；不得让各模块自行切换 ORM。

参考：

- [Prisma 支持的数据库](https://docs.prisma.io/docs/orm/reference/supported-databases)
- [Prisma MySQL Connector](https://docs.prisma.io/docs/orm/v6/overview/databases/mysql)

## 2.3 ID、时间与命名

- 所有核心实体使用应用层生成的 UUID；数据库列统一 `CHAR(36)`，不得混用自增整数、随机短串和其他 UUID 格式。
- 数据库字段使用 `snake_case`，TypeScript / Prisma 字段使用 `camelCase`，通过显式映射保持一致。
- 表名使用复数 `snake_case`。
- 所有系统时间写入 UTC，精度为毫秒；数据库使用 `DATETIME(3)`，API 使用 ISO 8601。
- 业务时间与系统时间分开，例如 `interviewedAt` 不得复用 `updatedAt`。
- 核心表默认包含 `createdAt`、`updatedAt`；需要软删除的表包含 `deletedAt`。

# 4. 公共 Enum 与状态机

所有 Enum 必须在单一公共模块定义，并与数据库映射、API 文档和测试共享。禁止在页面或各 Feature 中重复字符串。

```ts
export const UserStatus = ["ACTIVE", "DISABLED"] as const;
export const RoleCode = ["MEMBER", "ADMIN"] as const;
export const MemberStatus = ["ACTIVE", "REVOKED"] as const;

export const IdentityType = ["PHONE", "QQ", "QQ_OAUTH", "WECHAT_OAUTH"] as const;

export const JoinApplicationStatus = [
  "SUBMITTED",
  "INTERVIEW_PENDING",
  "INTERVIEW_PASSED",
  "INTERVIEW_REJECTED",
  "WITHDRAWN",
] as const;

export const InterviewResult = ["PASSED", "REJECTED"] as const;

export const ProvisionStatus = ["NOT_REQUIRED", "PENDING", "SUCCEEDED", "FAILED"] as const;

export const ProvisionSourceType = [
  "JOIN_APPLICATION",
  "INVITE_REDEMPTION",
  "ADMIN_CREATED",
] as const;

export const InviteCodeStoredStatus = ["ACTIVE", "REVOKED"] as const;
export const InviteCodeEffectiveStatus = [
  "NOT_STARTED",
  "ACTIVE",
  "REVOKED",
  "EXPIRED",
  "EXHAUSTED",
] as const;

export const AuditActorType = ["USER", "SYSTEM"] as const;
```

状态规则：

- `JoinApplicationStatus` 合法流转仅为：
  - `SUBMITTED → INTERVIEW_PENDING | INTERVIEW_PASSED | INTERVIEW_REJECTED | WITHDRAWN`
  - `INTERVIEW_PENDING → INTERVIEW_PASSED | INTERVIEW_REJECTED | WITHDRAWN`
- 终态再次修改需要独立管理员纠错能力、原因和审计，不属于普通审核接口。
- `INTERVIEW_PASSED` 只描述面试结果；发放结果由 `ProvisionStatus` 单独表达。
- 邀请码数据库只保存 `ACTIVE / REVOKED`；`NOT_STARTED / EXPIRED / EXHAUSTED` 根据生效时间、失效时间和计数派生，避免状态漂移。

# 5. 数据契约

## 5.1 User

职责：统一账户本体，不承载 QQ、报名或成员状态语义。

```text
id                CHAR(36) PK
status            VARCHAR(32) NOT NULL
display_name      VARCHAR(80) NULL
created_at        DATETIME(3) NOT NULL
updated_at        DATETIME(3) NOT NULL
deleted_at        DATETIME(3) NULL
```

规则：

- 禁用账号不等于删除成员资料。
- 被软删除账号不得登录，但历史外键保留。
- 不在 `users` 表中创建 `qq` 作为主键或跨业务关联键。

## 5.2 UserIdentity

职责：将手机号、QQ 及未来 OAuth 身份映射到统一 `User`。

```text
id                    CHAR(36) PK
user_id               CHAR(36) NOT NULL FK -> users.id
type                  VARCHAR(32) NOT NULL
identifier_normalized VARCHAR(191) NOT NULL
verified_at           DATETIME(3) NULL
created_at            DATETIME(3) NOT NULL
updated_at            DATETIME(3) NOT NULL
deleted_at            DATETIME(3) NULL
```

约束：

- 有效身份必须满足 `(type, identifier_normalized)` 全局唯一。
- QQ 规范化后只包含数字；手机号按项目确定的国家/地区规则规范化。
- 列表与日志默认脱敏，业务表只引用 `user_id`。
- OAuth 的 provider subject 写入同一身份模型或未来专用表，但不得新建另一套用户。

## 5.3 PasswordCredential

职责：当前阶段的密码登录凭据。

```text
user_id                CHAR(36) PK FK -> users.id
password_hash          VARCHAR(255) NOT NULL
must_change_password   BOOLEAN NOT NULL DEFAULT TRUE
password_changed_at    DATETIME(3) NULL
created_at             DATETIME(3) NOT NULL
updated_at             DATETIME(3) NOT NULL
```

只保存受支持算法生成的密码哈希。初始密码和一次性令牌不得以明文入库或写入日志。

## 5.4 Role 与 UserRole

```text
roles
  id          CHAR(36) PK
  code        VARCHAR(32) UNIQUE NOT NULL
  name        VARCHAR(64) NOT NULL
  created_at  DATETIME(3) NOT NULL

user_roles
  id           CHAR(36) PK
  user_id      CHAR(36) NOT NULL FK -> users.id
  role_id      CHAR(36) NOT NULL FK -> roles.id
  source_type  VARCHAR(32) NOT NULL
  source_id    CHAR(36) NULL
  granted_by   CHAR(36) NULL FK -> users.id
  granted_at   DATETIME(3) NOT NULL
  revoked_at   DATETIME(3) NULL
```

有效角色唯一性由数据库约束或受控的“有效关系键”实现，不能只靠先查后写。M0 Seed 必须可重复执行且不会生成重复角色。

## 5.5 MemberProfile

```text
id           CHAR(36) PK
user_id      CHAR(36) UNIQUE NOT NULL FK -> users.id
real_name    VARCHAR(64) NOT NULL
student_id   VARCHAR(32) NULL
class_name   VARCHAR(80) NULL
nickname     VARCHAR(64) NULL
avatar_url   VARCHAR(500) NULL
status       VARCHAR(32) NOT NULL
joined_at    DATETIME(3) NOT NULL
created_at   DATETIME(3) NOT NULL
updated_at   DATETIME(3) NOT NULL
deleted_at   DATETIME(3) NULL
```

撤销成员身份时保留 `User` 与历史数据，撤销 `MEMBER` 授权并将资料状态改为 `REVOKED`；不得物理删除维修历史。

## 5.6 JoinApplication

职责：保存公开报名事实。报名者可以没有 `User`。

```text
id                    CHAR(36) PK
ticket_no             VARCHAR(32) UNIQUE NOT NULL
recruitment_cycle     VARCHAR(32) NOT NULL
real_name             VARCHAR(64) NOT NULL
qq_normalized         VARCHAR(32) NOT NULL
phone_normalized      VARCHAR(32) NOT NULL
self_introduction     TEXT NULL
preferred_direction   VARCHAR(120) NULL
applicant_remark      VARCHAR(500) NULL
status                VARCHAR(32) NOT NULL
provision_status      VARCHAR(32) NOT NULL
privacy_consent_at    DATETIME(3) NOT NULL
submitted_at          DATETIME(3) NOT NULL
last_reviewed_at      DATETIME(3) NULL
created_at            DATETIME(3) NOT NULL
updated_at            DATETIME(3) NOT NULL
deleted_at            DATETIME(3) NULL
```

索引与约束：

- `ticket_no` 唯一且不可猜测。
- `(recruitment_cycle, qq_normalized)` 和 `(recruitment_cycle, phone_normalized)` 的重复策略必须由 Service 与数据库约束共同保证。
- 列表索引至少覆盖 `(status, submitted_at)`、`(provision_status, updated_at)`。
- QQ、手机号只用于招募联系与账号匹配，不作为 `User` 外键。

## 5.7 JoinApplicationReview

```text
id                  CHAR(36) PK
application_id      CHAR(36) NOT NULL FK -> join_applications.id
result              VARCHAR(32) NOT NULL
interviewed_at      DATETIME(3) NOT NULL
reviewer_user_id    CHAR(36) NOT NULL FK -> users.id
internal_note       VARCHAR(2000) NULL
created_at          DATETIME(3) NOT NULL
```

规则：每次处理新增一行，不覆盖旧面试记录。更新报名当前状态与插入 Review 必须在同一事务中完成。

## 5.8 InviteCode

```text
id                    CHAR(36) PK
code_digest           BINARY(32) UNIQUE NOT NULL
display_prefix        VARCHAR(12) NOT NULL
status                VARCHAR(32) NOT NULL
active_from           DATETIME(3) NULL
expires_at            DATETIME(3) NULL
max_uses               INT NOT NULL
used_count             INT NOT NULL DEFAULT 0
bound_qq_normalized    VARCHAR(32) NULL
bound_phone_normalized VARCHAR(32) NULL
created_by_user_id     CHAR(36) NOT NULL FK -> users.id
created_at             DATETIME(3) NOT NULL
updated_at             DATETIME(3) NOT NULL
revoked_at             DATETIME(3) NULL
deleted_at             DATETIME(3) NULL
```

规则：

- `code_digest = HMAC-SHA-256(serverPepper, normalizedCode)` 或经安全评审批准的等价方案。
- 明文邀请码只在创建成功响应中显示一次。
- 同一个邀请码允许多名成员重复使用，直到达到 `max_uses`、超过 `expires_at` 或被撤销。
- `max_uses >= 1`，`0 <= used_count <= max_uses`。
- 管理员可调整 `active_from`、`expires_at` 和 `max_uses`；`max_uses` 不得小于当前 `used_count`。
- `used_count` 是成功 Redemption 的事务计数，只读且不得通过管理 API 直接修改。
- 消费时使用行锁或等价原子更新，最后一个名额并发提交只能成功一次。
- `display_prefix` 仅供管理员识别，不足以还原邀请码。

## 5.9 InviteCodeRedemption

```text
id                  CHAR(36) PK
invite_code_id      CHAR(36) NOT NULL FK -> invite_codes.id
user_id             CHAR(36) NOT NULL FK -> users.id
member_profile_id   CHAR(36) NOT NULL FK -> member_profiles.id
idempotency_key     VARCHAR(128) UNIQUE NOT NULL
redeemed_at         DATETIME(3) NOT NULL
```

只有成功消费才写入 Redemption。失败尝试由限流/安全审计记录，不保存邀请码明文。

## 5.10 AccountProvision

```text
id                  CHAR(36) PK
source_type         VARCHAR(32) NOT NULL
source_id           CHAR(36) NOT NULL
idempotency_key     VARCHAR(128) UNIQUE NOT NULL
status              VARCHAR(32) NOT NULL
user_id             CHAR(36) NULL FK -> users.id
member_profile_id   CHAR(36) NULL FK -> member_profiles.id
attempt_count       INT NOT NULL DEFAULT 0
last_error_code     VARCHAR(64) NULL
created_at          DATETIME(3) NOT NULL
updated_at          DATETIME(3) NOT NULL
completed_at        DATETIME(3) NULL
```

必须对 `(source_type, source_id)` 建唯一键。同一报名、同一邀请码成功消费或同一管理员创建请求只能对应一个发放任务。

## 5.11 AuditLog

```text
id                CHAR(36) PK
actor_type        VARCHAR(16) NOT NULL
actor_user_id     CHAR(36) NULL FK -> users.id
action            VARCHAR(80) NOT NULL
target_type       VARCHAR(80) NOT NULL
target_id         CHAR(36) NOT NULL
request_id        VARCHAR(64) NOT NULL
result            VARCHAR(16) NOT NULL
before_summary    JSON NULL
after_summary     JSON NULL
error_code        VARCHAR(64) NULL
ip_digest         BINARY(32) NULL
user_agent_digest BINARY(32) NULL
created_at        DATETIME(3) NOT NULL
```

审计日志只追加，不提供普通更新/删除接口。密码、验证码、邀请码明文、令牌、密钥、完整手机号与完整 QQ 禁止进入摘要。

# 6. 事务与服务边界

后续页面和 API 不得直接散写 ORM 查询，统一通过 Service 调用。

```ts
interface JoinApplicationService {
  submit(input: SubmitJoinApplicationInput, context: PublicRequestContext): Promise<JoinReceipt>;
  review(input: ReviewJoinApplicationInput, actor: AuthorizedActor): Promise<JoinApplicationView>;
  retryProvision(applicationId: string, actor: AuthorizedActor): Promise<ProvisionView>;
}

interface InviteCodeService {
  create(input: CreateInviteCodeInput, actor: AuthorizedActor): Promise<CreateInviteCodeResult>;
  revoke(inviteCodeId: string, actor: AuthorizedActor): Promise<InviteCodeView>;
  redeem(
    input: RedeemInviteCodeInput,
    context: PublicRequestContext,
  ): Promise<MemberRegistrationResult>;
}

interface AccountProvisionService {
  provisionFromApplication(applicationId: string, idempotencyKey: string): Promise<ProvisionResult>;
  provisionFromInvite(redemptionId: string, idempotencyKey: string): Promise<ProvisionResult>;
}
```

## 6.1 面试通过事务

1. 锁定 `JoinApplication`。
2. 校验当前状态允许通过。
3. 插入 `JoinApplicationReview`。
4. 更新报名状态为 `INTERVIEW_PASSED`、发放状态为 `PENDING`。
5. 获取或创建唯一 `AccountProvision`。
6. 查找身份冲突；零个匹配时创建 `User`，一个匹配时复用，多个或矛盾匹配时失败并转人工。
7. 创建或激活 `MemberProfile`，授予 `MEMBER`。
8. 生成一次性初始化凭据，只保存哈希。
9. 标记发放成功并写审计日志。

如果外部通知不可与数据库事务一致完成，采用事务内写 Outbox、事务后发送的方式；M0 可只预留接口，不实现通知渠道。

## 6.2 邀请码消费事务

1. 规范化邀请码并计算摘要。
2. 锁定匹配的 `InviteCode`。
3. 校验未撤销、未过期、未耗尽且绑定条件匹配。
4. 以手机号/QQ 身份查找或创建统一 `User`，冲突时停止。
5. 创建或激活 `MemberProfile`，授予 `MEMBER`。
6. 原子增加 `usedCount`，插入 `InviteCodeRedemption`。
7. 创建成功 `AccountProvision` 并写审计日志。

整个流程失败时回滚，不得出现“邀请码已扣次数但成员未创建”的中间状态。

# 7. API 规范

## 7.1 路径与版本

- 统一前缀：`/api/v1`
- 资源名使用复数 kebab-case。
- 管理接口位于 `/api/v1/admin/*`，但路径不是权限边界，服务端仍需校验权限。
- 状态动作使用子资源或明确动作路径，禁止万能 `PATCH status=<任意值>` 绕过状态机。

## 7.2 成功响应

```json
{
  "success": true,
  "data": {},
  "meta": {
    "requestId": "req_..."
  }
}
```

分页响应在 `meta.pagination` 返回：

```json
{
  "page": 1,
  "pageSize": 20,
  "total": 42,
  "totalPages": 3
}
```

## 7.3 错误响应

```json
{
  "success": false,
  "error": {
    "code": "INVITE_CODE_EXPIRED",
    "message": "邀请码已失效",
    "fieldErrors": {}
  },
  "meta": {
    "requestId": "req_..."
  }
}
```

生产环境不得返回堆栈、SQL、表名、凭据或账户存在性细节。

## 7.4 必须冻结的接口

### POST `/api/v1/join-applications`

请求：

```json
{
  "realName": "张三",
  "qq": "123456789",
  "phone": "13800000000",
  "selfIntroduction": "可选",
  "preferredDirection": "可选",
  "privacyConsent": true
}
```

响应 `201`：`{ id, ticketNo, status, submittedAt }`。重复有效报名可以返回 `200` 与原回执，或返回稳定 `JOIN_APPLICATION_DUPLICATE`；M0 必须选择一种并写契约测试，推荐返回原回执以支持安全重试。

### GET `/api/v1/admin/join-applications`

参数：`page`、`pageSize`、`status`、`provisionStatus`、`submittedFrom`、`submittedTo`、`query`。仅管理员/社长；列表中的 QQ 与手机号默认脱敏。

### GET `/api/v1/admin/join-applications/:id`

返回报名详情、Review 时间线与 Provision 摘要。需要 `join:read`。

### POST `/api/v1/admin/join-applications/:id/reviews`

请求：

```json
{
  "result": "PASSED",
  "interviewedAt": "2026-09-15T08:00:00.000Z",
  "internalNote": "可选"
}
```

需要 `join:review`。`PASSED` 触发幂等账号发放。响应包含报名状态和发放状态。

### POST `/api/v1/admin/join-applications/:id/provision/retry`

仅 `ProvisionStatus = FAILED` 可调用。必须携带 `Idempotency-Key`，不得创建新的来源任务。

### POST `/api/v1/admin/invite-codes`

请求包含 `expiresAt`、`maxUses`、可选 `boundQq` / `boundPhone`。响应中的 `plainCode` 只出现一次，后续查询不再返回。

### GET `/api/v1/admin/invite-codes`

返回 `displayPrefix`、有效状态、使用数、有效期和创建者；永不返回摘要或明文。

### PATCH `/api/v1/admin/invite-codes/:id`

允许管理员更新 `activeFrom`、`expiresAt` 和 `maxUses`。不允许修改邀请码明文、`codeDigest` 或直接写 `usedCount`；`maxUses < usedCount` 时返回 `INVITE_CODE_USAGE_LIMIT_INVALID`。更新必须写审计日志。

### POST `/api/v1/admin/invite-codes/:id/revoke`

幂等撤销。已撤销再次请求返回当前状态，不报内部错误。

### POST `/api/v1/member-registrations/invite`

请求包含邀请码、QQ、手机号、姓名、学号、班级及密码或一次性初始化所需字段。成功后创建/复用统一账户并返回成员初始化结果；不得通过错误消息区分“某手机号已注册”和“某 QQ 已注册”等可枚举信息。

## 7.5 稳定错误码

# 9. 软删除与数据保留

软删除适用于：

- `users`
- `user_identities`
- `member_profiles`
- `join_applications`
- `invite_codes`（业务操作优先使用撤销）

默认查询必须排除 `deleted_at IS NOT NULL`。

以下记录原则上不可由业务接口删除：

- `join_application_reviews`
- `invite_code_redemptions`
- `account_provisions`
- `audit_logs`

GreatSQL 不支持通用的条件唯一索引语义时，不得只写“软删除后允许复用”而不实现约束。M0 必须选择并测试一种策略：

1. 对永不复用的登录身份保留全局唯一键；或
2. 增加受控的有效记录键/生成列，并以唯一约束保证只有一条有效记录。

身份、QQ、手机号默认采用全局不复用策略，除非后续有经过审计的身份转移流程。

- `/handbook/` 仍由 mdBook 构建为同域静态文件，既有 `pnpm build` 文档构建链路必须保留。
- GreatSQL 仅允许服务端访问，浏览器不得直连数据库。
- 反向代理、进程管理和健康检查的具体实现可由部署任务完成，但 M0 必须提供运行时所需端口、健康检查和优雅关闭契约。

# 11. Migration 与 Seed 策略

## 11.1 开发流程

1. 修改唯一 Schema 源。
2. 生成命名清晰的 Migration。
3. 人工审查 SQL 是否兼容固定 GreatSQL 版本。
4. 在空库执行全部 Migration。
5. 在包含上一版本数据的测试库执行升级。
6. 运行 Seed、集成测试和约束测试。
7. 提交 Schema、Migration、契约与测试，禁止只提交生成客户端。

## 11.2 环境规则

- 本地开发可使用 `migrate dev`。
- CI、预发布和生产只使用 `migrate deploy` 或团队批准的等价命令。
- 禁止在共享、预发布、生产环境使用 `db push`。
- 禁止手工改生产表后再补 Migration。
- 破坏性变更采用 expand-and-contract：先加可空列/新表并双读写，再回填和切换，最后在后续版本收紧或删除。
- Migration 失败优先修复并前向发布；数据恢复依赖发布前备份与演练，不承诺自动向下回滚破坏性 DDL。

## 11.3 Seed

Seed 至少创建：

```text
Role MEMBER
Role ADMIN
```

Seed 必须幂等。禁止写入真实成员、真实手机号、真实 QQ、真实邀请码或默认生产管理员密码。

# 14. 验收标准

## 14.1 数据库与迁移

- 固定 GreatSQL 版本可以启动并接受应用连接。
- 空库可从零执行全部 Migration。
- 上一版本测试库可前向升级，数据不丢失。
- Seed 重复执行两次不产生重复角色。
- 所有表使用 InnoDB、`utf8mb4` 和统一排序规则。
- `pnpm lint`、`pnpm build` 通过；标准 build 不绕过站内 mdBook 构建。

## 14.2 数据契约

- `User.id` 是账号和业务关联的唯一主体。
- QQ/手机号只存在于报名数据或身份映射，不被任何业务表当作用户外键。
- 一名用户最多一个有效 `MemberProfile`。
- 同一有效身份不能绑定两个用户。
- Enum、API 错误码与数据库映射只有一个事实来源。

## 14.3 报名与账号发放

- 公开报名经过服务端校验并真实写入 GreatSQL。
- 同一招募周期重复提交不会产生重复有效报名。
- 管理员可以在 Service/API 测试中标记通过或未通过。
- 面试通过可创建新 `User`，也可安全升级已存在的普通 `User`。
- 同一报名重复通过、请求重试或任务重跑不会产生重复用户、成员档案或角色。
- 身份冲突进入明确失败状态，不会自动覆盖数据。

## 14.4 邀请码

- 数据库无法读取邀请码明文。
- 未到生效时间、过期、撤销、耗尽或绑定不符的邀请码均被拒绝并返回稳定错误码。
- 同一邀请码可在 `maxUses` 范围内被不同成员重复使用；后台可调整生效起止时间和最大次数，但不能直接修改 `usedCount`。
- `maxUses = 1` 时并发 10 次消费最多一笔成功。
- 成功消费后 `usedCount`、Redemption、User、MemberProfile、UserRole 和 Provision 一致提交。
- 任一步失败时事务回滚，不扣除使用次数。

## 14.5 权限、审计与软删除

- 未登录和普通成员不能调用管理员招募/邀请码接口。
- 管理操作记录 actor、action、target、requestId、结果与脱敏摘要。
- 日志中不存在密码、一次性令牌、邀请码明文、验证码和完整联系方式。
- 软删除对象默认查询不可见，历史外键与审计仍可追踪。
- 审计、Redemption、Provision 无普通删除接口。

## 14.6 主题与现有 Phase 2 兼容

- M0 不修改现有视觉系统和公共组件 API。
- 后续报名/后台页面契约保留 Loading、Empty、Error 与权限拒绝状态。
- 所有状态包含文字语义，不要求页面只靠颜色区分。
- 若新增状态语义色，必须先更新设计系统和两套主题，不得在业务页面写死颜色。

# 15. 禁止事项

- 禁止把 QQ 号、手机号、邀请码作为 `User.id`。
- 禁止通过 `MemberProfile.role` 单字段替代 `Role / UserRole`。
- 禁止面试通过时先创建账号、再无事务地更新报名。
- 禁止邀请码“先查剩余次数，再普通更新”造成并发超卖。
- 禁止保存、记录或二次查询邀请码明文。
- 禁止在日志和错误响应中输出密码哈希、令牌、验证码、数据库连接串或完整 PII。
- 禁止直接物理删除报名、成员、维修、Redemption、Provision 或 AuditLog。
- 禁止各模块私自新增 Enum 拼写、API 信封或错误格式。
- 禁止在生产或共享数据库使用 `db push`。
- 禁止修改已应用 Migration；需要变更时新增 Migration。
- 禁止提交 `.env`、数据库备份、真实成员数据或测试用真实联系方式。
- 禁止为了 M0 修改 `zafu-pchospital-site/`、重做 Header/Footer、引入第二套 UI/CSS/状态管理体系。
- 禁止绕过 `pnpm` 或删除 `pnpm-lock.yaml`。
