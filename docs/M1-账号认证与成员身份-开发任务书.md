# 2. M1 目标

M1 负责在 M0 数据契约之上完成：

> 统一账户认证、成员身份建立、受保护会话，以及报名通过和邀请码注册的可运行闭环。

M1 完成后应能稳定跑通：

```text
报名通过 / 邀请码注册 / 管理员直接创建
                  ↓
建立或复用统一 User
                  ↓
绑定 QQ / 手机号身份
                  ↓
创建 MemberProfile + MEMBER Role
                  ↓
QQ 号 + 密码登录
                  ↓
首次登录强制修改初始密码
                  ↓
进入受保护成员区域
```

核心边界：

- `User.id` 是用户本体。
- QQ 号只是 `UserIdentity(type=QQ)`，不能作为主键或跨领域外键。
- Role 和 MemberProfile 必须从数据库真实状态判断，不能信任客户端字段或 Cookie 中的角色。
- 报名状态、面试结果、账号发放状态和登录状态彼此独立。

# 5. M1 新增数据实体

M1 允许通过一个新的前向 Migration 增加认证运行所需实体。不得修改已经提交的 M0 Migration。

## 5.1 AuthSession

数据库只保存会话令牌摘要，不保存浏览器 Cookie 中的明文令牌。

```text
id                 CHAR(36) PK
user_id            CHAR(36) NOT NULL FK -> users.id
token_digest       BINARY(32) UNIQUE NOT NULL
created_at         DATETIME(3) NOT NULL
last_seen_at       DATETIME(3) NOT NULL
expires_at         DATETIME(3) NOT NULL
revoked_at         DATETIME(3) NULL
ip_digest          BINARY(32) NULL
user_agent_digest  BINARY(32) NULL
```

建议索引：

```text
UNIQUE(token_digest)
INDEX(user_id, revoked_at, expires_at)
INDEX(expires_at)
```

规则：

- 浏览器令牌使用密码学安全随机数，长度至少 32 字节。
- `tokenDigest = HMAC-SHA-256(AUTH_SECRET, rawToken)` 或安全评审通过的等价方案。
- Cookie 明文只存在于客户端 Cookie 与当前请求内存。
- 读取会话时同时校验 Session、User、UserRole 和 MemberProfile 的当前状态。
- 禁用或软删除 User 时，即使 Session 尚未过期也必须拒绝访问。

## 5.2 LoginThrottle

登录限流必须可在多实例部署下保持一致，不能只依赖单进程内存。

```text
key_digest         BINARY(32) PK
failed_count       INT NOT NULL
window_started_at  DATETIME(3) NOT NULL
blocked_until      DATETIME(3) NULL
updated_at         DATETIME(3) NOT NULL
```

`keyDigest` 根据规范化 QQ 和请求 IP 的安全摘要构成，不存储密码、完整 QQ 或完整 IP。成功登录后按策略清理或重置；失败响应不得泄露账号是否存在。

若实现团队选择复用已有共享限流基础设施，必须达到同等多实例安全性，并在交付报告中说明，不得重复创建第二套限流契约。

# 6. 登录与会话契约

## 6.1 登录标识

当前登录表单使用：

```text
QQ号 + 密码
```

服务端处理顺序：

1. 规范化 QQ。
2. 通过 `UserIdentity(type=QQ, identifierNormalized)` 查找统一 User。
3. 校验 User 未删除且状态为 `ACTIVE`。
4. 校验 `PasswordCredential`。
5. 使用恒定风格的失败响应，不区分“账号不存在”和“密码错误”。
6. 创建数据库 Session 并设置 Cookie。
7. 读取有效 Role 和 MemberProfile，返回当前用户摘要。
8. 写入成功或失败安全审计。

不存在账号时仍应执行安全的占位密码校验，降低通过响应耗时枚举账号的风险。

## 6.2 Cookie

建议固定：

```text
Name      pc_hospital_session
HttpOnly  true
Secure    生产环境 true
SameSite  Lax
Path      /
Max-Age   与服务端 Session expiresAt 一致
```

要求：

- Cookie 只保存随机会话令牌，不保存 userId、QQ、角色或权限。
- 退出登录时撤销数据库 Session，并让浏览器 Cookie 立即失效。
- 所有带 Cookie 的写接口校验同源 `Origin / Host`；不得仅依赖 SameSite 防御 CSRF。
- 会话续期设置最小更新时间间隔，避免每个请求都写数据库。
- Cookie 缺失、摘要不存在、已过期或已撤销统一视为未登录。

## 6.3 会话有效期

默认建议：

```text
绝对有效期：30 天
活跃续期：距离过期不足 7 天时续期
```

具体值集中放在服务端认证配置中，不散落在 Route 和组件里。修改策略需要同步测试与文档。

## 6.4 受保护请求

新增统一入口，例如：

```ts
getCurrentSession(request);
requireAuthenticatedUser(request);
requireAuthorizedActor(request, permission);
```

`requireAuthorizedActor` 必须基于数据库当前状态构造 actor，再复用 M0 的 `authorizeUser` / `requirePermission`。客户端传入的角色、权限、userId 和 memberId 一律不可信。

Next.js 中间件最多用于无 Cookie 时的快速导航，不得在 Edge Middleware 中直接使用 Prisma，也不能把 Middleware 当作最终权限校验。

# 7. 密码与首次登录

## 7.1 密码规则

- 继续复用 M0 的 scrypt 实现。
- 密码长度 **6–128** 个字符。
  > 2026-09 第十一轮验收时从 12 位下调到 6 位（产品决定：本地 / 验收环境需要一个能口头
  > 传达的短口令）。长度策略只在 `src/lib/security/password-policy.ts` 定义一次，
  > 表单约束、服务端校验、`hashPassword` 兜底三处共用；**登录表单不设下限** ——
  > 登录是校验密码而不是设置密码，写死下限会让短口令账号在前端就提交不出去。
  > 安全上的补偿是登录节流：同一 QQ + IP 15 分钟内失败 5 次即锁定。
- 数据库只保存哈希。
- 登录、改密和重置流程不得记录密码、哈希或初始化凭据。
- 新密码不得与确认密码不一致；前后端均提示，但服务端校验是最终依据。

## 7.2 初始密码

以下来源产生初始密码或一次性初始化凭据，`mustChangePassword = true`：

- 报名通过后自动发放
- 管理员直接创建成员
- 管理员重置密码

明文只允许在成功响应或受控发送渠道中出现一次，之后不可查询。

邀请码注册由成员本人设置密码，因此成功后必须写入：

```text
mustChangePassword = false
passwordChangedAt = 注册完成时间
```

不得错误地把用户自设密码当作管理员初始密码。

## 7.3 强制改密

登录成功但 `mustChangePassword = true` 时：

- 可以建立受限 Session。
- 只允许访问当前用户查询、修改密码和退出登录。
- 访问 `/member` 或其他业务接口时返回稳定错误码 `PASSWORD_CHANGE_REQUIRED`。
- 页面统一跳转 `/account/change-password`。
- 修改成功后将 `mustChangePassword = false`、写入 `passwordChangedAt`。
- 撤销该用户其他有效 Session；当前 Session 可轮换令牌后继续使用。
- 写入安全审计，不记录密码内容。

# 8. 成员身份建立流程

## 8.1 报名通过

复用 M0 的 `JoinApplicationService.review()` 与 `AccountProvisionService`：

```text
管理员鉴权并提交 PASSED
        ↓
新增 JoinApplicationReview
        ↓
报名状态 = INTERVIEW_PASSED
        ↓
发放状态 = PENDING
        ↓
幂等创建/复用 User
        ↓
创建或激活 MemberProfile
        ↓
授予 MEMBER
        ↓
创建初始密码凭据
        ↓
Provision = SUCCEEDED / FAILED
```

要求：

- 重复请求不得产生重复账号、成员档案、Role 或 Provision。
- 账号身份冲突返回 `ACCOUNT_IDENTITY_CONFLICT`，不得自动覆盖。
- 发放失败保留面试通过状态，管理员可用原 Provision 安全重试。
- 一次性初始化凭据不得在报名详情接口中重复返回。

## 8.2 邀请码注册

复用 `InviteCodeService.redeem()`：

- 同一个邀请码可以被不同成员重复使用，直到达到 `maxUses`。
- 校验 `activeFrom`、`expiresAt`、`status`、绑定 QQ/手机号和剩余次数。
- `usedCount` 只允许在兑换事务中原子增加。
- User、Identity、MemberProfile、UserRole、Redemption、Provision、AuditLog 和计数必须同一事务提交。
- 幂等重试返回第一次成功结果，不重复扣次数。
- 注册者本人设置的密码不要求首次修改。

## 8.3 管理员直接创建成员

新增受控 Service/API，输入至少包含：

```text
realName
qq
phone
可选 studentId / className / nickname
```

系统创建或复用统一 User、创建 MemberProfile、授予 MEMBER 并生成一次性初始凭据。来源记录为 `ADMIN_CREATED`，写 `AccountProvision` 与 `AuditLog`，并遵守与报名发放相同的冲突和幂等规则。

# 9. API 任务

所有接口使用 M0 API 信封、requestId、错误码和字段错误格式。

## 9.1 认证接口

```text
POST /api/v1/auth/login
POST /api/v1/auth/logout
POST /api/v1/auth/password/change
GET  /api/v1/me
```

### `POST /api/v1/auth/login`

请求：

```json
{
  "qq": "123456789",
  "password": "用户输入的密码"
}
```

成功返回当前用户摘要：

```text
userId
displayName
roles
memberProfile 摘要
mustChangePassword
```

密码不得出现在响应。账号不存在、密码错误统一返回 `AUTH_INVALID_CREDENTIALS`。

### `POST /api/v1/auth/logout`

幂等撤销当前 Session 并清除 Cookie。已失效 Session 再次退出仍返回成功。

### `POST /api/v1/auth/password/change`

首次改密时要求当前 Session；普通主动改密还必须校验旧密码。修改成功后撤销其他 Session，并轮换当前 Session。

### `GET /api/v1/me`

返回数据库当前状态，不从客户端 Cookie 读取角色。未登录返回 `UNAUTHENTICATED`；被禁用返回 `FORBIDDEN`。

## 9.2 招募接口

接线并测试 M0 已冻结接口：

```text
GET  /api/v1/admin/join-applications
GET  /api/v1/admin/join-applications/:id
POST /api/v1/admin/join-applications/:id/reviews
POST /api/v1/admin/join-applications/:id/provision/retry
```

列表接口支持分页、状态、发放状态、时间范围和脱敏查询。普通成员不得访问。报名详情中的手机号、QQ、内部备注和 Provision 仅在管理员权限下返回。

## 9.3 邀请码接口

接线并测试：

```text
POST  /api/v1/admin/invite-codes
GET   /api/v1/admin/invite-codes
PATCH /api/v1/admin/invite-codes/:id
POST  /api/v1/admin/invite-codes/:id/revoke
POST  /api/v1/member-registrations/invite
```

管理员只可修改 `activeFrom`、`expiresAt`、`maxUses`；`usedCount` 只读。明文邀请码只在创建成功响应中返回一次。

## 9.4 成员管理核心接口

M1 新增并冻结：

```text
POST /api/v1/admin/members
POST /api/v1/admin/members/:id/disable
POST /api/v1/admin/members/:id/enable
POST /api/v1/admin/members/:id/password-reset
```

这些接口供 M6 后台使用。禁用账号后所有受保护请求立即失效；实现可以同步撤销 Session，但即使撤销失败，实时 User 状态校验也必须阻止访问。

## 9.5 新增稳定错误码

在 `src/lib/api/errors.ts` 单一来源中补充：

```text
AUTH_INVALID_CREDENTIALS
AUTH_SESSION_INVALID
AUTH_SESSION_EXPIRED
AUTH_RATE_LIMITED
PASSWORD_CHANGE_REQUIRED
PASSWORD_CURRENT_INVALID
PASSWORD_CONFIRMATION_MISMATCH
ACCOUNT_DISABLED
MEMBER_PROFILE_INACTIVE
```

如错误码命名需要调整，必须同步 Type、Route、Service、客户端、Contract、测试和文档。

# 11. 安全与审计

至少记录：

```text
auth.login.succeeded
auth.login.failed
auth.logout
auth.password.changed
auth.password.reset
auth.session.revoked
member.created
member.enabled
member.disabled
join.review.created
account.provision.retried
invite.code.created
invite.code.policy_updated
invite.code.revoked
invite.code.redeemed
```

要求：

- 失败登录日志只保存安全摘要，不记录密码和完整 QQ/IP。
- 登录失败提示不能暴露账号存在性。
- 管理员敏感操作记录 actor、target、requestId、结果和脱敏摘要。
- Session、密码、初始化凭据、邀请码明文不得进入日志、错误响应或 URL。
- 所有公开写接口有限流。
- 所有 Cookie 鉴权写操作执行同源校验。
- 禁用 User、撤销成员身份和软删除状态必须在每次受保护请求时生效。

## 12.2 GreatSQL 集成测试

- 正确密码登录成功，错误密码失败。
- 不存在账号与错误密码返回相同公开错误。
- 登录限流在并发请求下生效。
- 原始 Session token 不出现在数据库。
- 登出后 Session 不可继续使用。
- 过期、撤销、禁用用户 Session 被拒绝。
- 初始账号必须改密；改密后其他 Session 被撤销。
- 邀请码注册写入 User、Identity、MemberProfile、UserRole、Redemption、Provision 和 AuditLog。
- 邀请码注册者自设密码 `mustChangePassword=false`。
- 报名通过重复请求不重复发放。
- 管理员直接创建成员幂等且账号冲突不覆盖。
- 普通成员不能调用管理员接口。

# 13. 多人协作拆分

可以并行拆为以下工作包：

| 工作包                 | 负责内容                                     | 主要依赖              |
| ---------------------- | -------------------------------------------- | --------------------- |
| M1-A Session           | AuthSession、登录限流、Cookie、认证 Service  | M0 DB/API/Auth        |
| M1-B Auth UI           | `/login`、改密、`/me`、受保护入口            | M1-A                  |
| M1-C Recruitment       | 报名后台 API、审核、发放重试、`/join` 接线   | M1-A + M0 recruitment |
| M1-D Invitation        | 邀请码管理 API、兑换 API、`/register/member` | M1-A + M0 invitations |
| M1-E Member Admin Core | 管理员创建、禁用、启用、重置密码 Service/API | M1-A                  |
| M1-F Security QA       | 权限、审计、并发、契约和视觉回归             | A–E                   |

高冲突文件只指定一名契约负责人合并：

- `prisma/schema.prisma`
- `prisma/migrations/`
- `src/types/contracts.ts`
- `src/lib/api/errors.ts`
- `docs/contracts/`

其他协作者不得各自新增同义 Enum、错误码、Session 模型或 API 信封。

推荐合并顺序：

```text
Session Schema / Migration
↓
认证 Service 与 Cookie
↓
登录、改密、/me 与受保护入口
↓
报名审核与账号发放 API
↓
邀请码管理、兑换 API 与注册页
↓
管理员成员核心 API
↓
/join 接线、全链路与安全回归
```

# 14. 禁止事项

- 禁止把 QQ、手机号、学号或 Cookie 当作 User 主键。
- 禁止在 Cookie 中保存角色、权限或完整用户资料。
- 禁止保存明文 Session token、密码、初始化凭据或邀请码。
- 禁止由客户端决定 userId、Role、Permission、Provision 状态或 `usedCount`。
- 禁止页面、组件或 Route Handler 直接查询 Prisma。
- 禁止使用内存 Session 作为生产唯一会话存储。
- 禁止只隐藏前端按钮而不做服务端授权。
- 禁止重复实现 M0 已有账号发放、邀请码事务和 API 信封。
- 禁止修改已提交的 M0 Migration；Schema 变化必须新增前向 Migration。
- 禁止在共享或生产数据库使用 `prisma db push`。
- 禁止提前实现 M2–M7 页面和业务。
- 禁止全量重构或格式化无关文件。
- 禁止修改现有主题架构、Header/Footer 公共 API 或 mdBook 构建链路。
